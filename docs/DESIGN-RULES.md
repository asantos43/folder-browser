# Design rules by area (read the section before you touch that area)

Moved out of `CLAUDE.md` to keep what every session loads small. The **invariants that always apply** (the authorised roots, safe writes, the trash, a snapshot is a page, and the like) stay in `CLAUDE.md`; the rules of each feature are here, with the files and functions they name. Read the section of the area you change; they are exact, and several are there because something broke.

## Settings registry

Portable settings use `fb:settings-export`, `fb:settings-import-preview`, `fb:settings-import-apply`, `fb:settings-reset-all` and `fb:settings-show-file`, restricted to the interface's top frame. Export and import accept no arguments: only the main process opens the native save/open dialog and selects the path. Export reuses the same-directory temporary write and rename. Import asynchronously reads at most 256 KB plus one sentinel byte (the budget enforced by the oversized-file test), closes the handle, and refuses malformed JSON without modifying settings. No filesystem work runs on the renderer thread; only one preview per window is retained.

The main process owns the preview and returns a token, each changed key's current/new values, unknown keys, invalid values, and `needsConfirm`. Applying requires that token and explicit `confirmed: true`; safety changes additionally require `safetyConfirmed: true`, obtained by a second highlighted confirmation in the UI even when returning to a default. Unknown keys and invalid values are listed and skipped; valid listed changes are applied only after confirmation. A preview with changed current values is refused as stale; applying consumes it, and a new preview attempt invalidates the previous one even on cancellation/error. Reset All uses the existing renderer `ConfirmDialog` (Cancel initially focused) and the main process strictly requires a sole `true` argument. Both operations reuse `SettingsStore` and broadcast only actual changed ids. Renderer batches are settled before portable operations. Show Settings File reveals only the fixed `userData/settings.json` path; it does not authorise an editor root. Hand edits are loaded on the next start, covered by reopening the host after changing the real file. Export keeps the existing format (only nondefault registered values); imports merge their listed values, so absent keys retain current values.

`core/settings/` is pure TypeScript. Declare defaults and validators once in the registry; core ids use `category.name`, plugin ids use `<plugin>:<name>`. `SettingsStore` owns values, retains unknown JSON keys, reports invalid known values and batches persistence through an injected atomic writer. Plugin contributions validate as a batch and return an idempotent removal function. Portable import is preview-only until explicitly applied; any `safety` option requires confirmation.

`electron/settings-host.ts` owns `settings.json` at the fixed `app.getPath('userData')` location. It loads and validates the file synchronously before the first window; the preload makes exactly one synchronous `fb:settings-get-all` request and caches values and notices. Only the top frame of `fb-ui://` may use the settings IPC. `fb:settings-set` accepts at most 100 `[id, value]` pairs per message, discards invalid pairs individually, and persists through a same-directory temporary file and rename, grouped over 100 ms. Actual changed ids are broadcast to every interface window on `fb:settings-changed`; pending writes flush before quit, when the last window closes and once more at `will-quit` (a window that was closing sends its last change after the first flush). The preload's `all()` asks the main process each time (a synchronous call), which also settles every `set` sent before it from that window.

The renderer reads `window.fb.settings.all()` once at startup; each setting validates its value and falls back to its declared default if invalid. Theme and language use this same store, and `applyInitialTheme` applies the synchronous value before React renders. `set` updates that setting's external-store snapshot immediately and sends its id/value pair at once when no call went in the last 100 ms (a window closed a moment later keeps the change) and otherwise queues it, with at most one `settings.set` call per 100 ms; the pairs of that period go together and the latest value for each id wins; `pagehide` and `beforeunload` send what is waiting. The migration is the exception: its pairs always wait for the 100 ms batch. `onChanged` ignores an id that still has a newer local value waiting. `onChanged` reads a current snapshot and updates and notifies only the stores for the listed ids. The preload refreshes its cache (a synchronous `fb:settings-get-all`) before it calls an `onChanged` listener, so `all()` inside the listener returns the new values. With no settings bridge (unit tests), the existing `fb:<legacy-key>` localStorage path remains active. Startup settings notices use the existing notification mechanism, with English and Brazilian Portuguese text.

The one-time migration marker is `fb:settings-migrated` in localStorage. Before marking it, migration submits valid legacy values only for ids absent from the persisted settings file; it leaves the legacy keys in place. Invalid legacy values are ignored. Migration uses the same outgoing batch and marks completion after submitting it; if nothing needs migration, it marks completion after synchronous setting registration. The bridge's `all()` includes every registered id with its default, and the store never writes a default value to the file, so an id whose bridge value equals its declared default (or is missing) counts as absent and takes the valid legacy value; a file edited by hand to hold a default value explicitly is overwritten by the legacy value in this one run.

The Settings page is generated from the registry: declare a setting with its type, default, category, `label` and `description` i18n keys, and add those two texts to both catalogs. Reuse existing keys for choice labels (`choiceLabels`) and category headings (`categoryLabel`); optional `keywords` are also i18n keys. There is no renderer list to extend. Six controls cover boolean, choice, number, string, colour and newline-separated string lists. Categories retain their declaration order; plugin ids (`<plugin>:<name>`) get a “Plugins ▸ <plugin>” section only while registered. Registry subscriptions update an already open page when contributions are added or removed.

Search normalizes accents and case and indexes labels, descriptions and keywords once per registry/language change; `useDeferredValue` and the memoized results let the search field commit before filtering the list. Modified compares the current value with the declared default, including list contents. Reset uses `Setting.reset` and `fb:settings-reset`, which validates unknown input and the top interface frame before calling `SettingsStore.reset`; section resets include rows hidden by search and batch ids in messages of at most 100. A reset cancels an older pending set for that id. Show Only Modified combines with search. `restart: true` displays a restart-required note; there is currently no relaunch API, so the user restarts the application normally. Ordinary changes continue through `Setting.set` and the existing settings bridge, including theme and language. Budgets: median of 20 filters of 500 entries below 10 ms, initial React render of 17 + 500 entries below 200 ms, and input commits before the deferred results; component tests enforce these limits. Large sections mount at most the nearby controls using one IntersectionObserver, keep placeholders with measured heights, and retain a focused control. The initial window is 40 rows per section; the 17 builtin options remain fully mounted.

## Office documents

An office document is drawn by `src/docs/{docx,pptx,odf}.ts`, built by `vite.docs.config.ts` into `dist/docs/` (one classic script each; `npm run build` runs `build:docs`). The main process gives each open document a token and serves `fb-doc://<token>/` (the page, `/_file`, `/_v/<flavour>.js`; `electron/doc-protocol.ts`) with a CSP that has `sandbox allow-scripts`, `default-src 'none'` and no network; the interface shows it in `<iframe sandbox="allow-scripts">`, which has an opaque origin and cannot reach `window.fb`. The page tells the interface how it went with `postMessage` (`DocMessage`). A new library or format means a new flavour in `core/docs.ts`, never a script in the interface itself. The odr-core build defines `import.meta.url` (`vite.docs.config.ts`) and needs `connect-src data:` for the WebAssembly it carries inside.

## Zoom, Find and Print of a document

The zoom of a document is the same as a snapshot page's (the frame is laid out at 1/zoom and scaled); keys and wheel inside it come as `DocReport` messages (`wheel`, `zoom`) and only the tab in front is obeyed; Find registers the document's frame as `fileTarget`; Print opens a hidden window on `fb-doc://<token>/?print=1`. The hex view reads `findToken` (Ctrl+F focuses its own box; `EditorGroup` shows no `FindBar` for it).

## A file shown as its bytes (Open as Hex)

A file can be shown as its bytes by choice: `Tab.as = 'hex'` (key `x:<id>:<path>`, `hexKey`), opened by `open-file` with `as: 'hex'` (tree menu **Open as Hex**, **View as hex** on the card of a file that is not shown); `kindOf` answers `hex` for it, and the session keeps it. `FileView` has no state for this: it asks (`onHex`) and the workspace opens the tab. Documents are kept mounted by `EditorGroup` (not by `FileView`), drawn on first view.

## Changing the disk (`core/fs/ops.ts`)

Changing the disk (`core/fs/ops.ts`) is done by the main process on a root and a relative path; the parent is resolved and the item is `lstat`ed, so a symbolic link is the link; nothing is replaced (a copy takes a free numbered name); the root, a ZIP's entries (the registry sends those to `core/archive/edit.ts`), a ZIP root and the trash are `unsupported` in `ops.ts` itself. The renderer has no `process`: a `core/` module that the interface imports (`names.ts`) must not read it at module level or by default without a guard (the interface passes `window.fb.platform`). The tree's inline field, the delete and move dialogs and the reducer's `path-changed` / `path-removed` are the interface's side; a new operation means a new `fb:fs-*` channel validated as `unknown`, a result `OpResult`, and a test that a path leaving the root is refused.

## Editing text (phase 3)

Editing (phase 3): the text of an editor tab lives in `src/state/editors.ts` (`EditorBuffer`, by tab key), not in the component; `saveBuffer` is the one way to write it; the reducer's `dirty` is what the tab, the close guard and the window read; `Workbench`'s `dispatch` is a guard for the actions that close tabs (use `rawDispatch` for what must not ask). A window with tabs that have changes does not close until the interface answers (`fb:unsaved`, `fb:close-requested`, `fb:leave`): an e2e spec must `destroy()` its windows in `afterEach` or it hangs. Never write a file from the renderer's text without `saveEdited` (temporary file, rename, version check).

## Unsaved changes and hot exit (phase 3a)

Unsaved changes (phase 3a, hot exit): `src/state/drafts.ts` writes a draft (`core/drafts.ts`, `userData/drafts/`) 1.2 s after a tab's last change and deletes it when the tab is no longer dirty; `restoreDrafts` reopens the tabs at start and `EditView`/`HexEditView` build their buffer from the draft (the disk content is the saved state, the draft's `base` is the version, so Save still detects a changed file). With the `hotExit` setting on the window closes without asking after `flushDrafts`. Hex editing (`core/hexEdit.ts`, `HexEditView`) is for folder-root files up to 16 MiB and saves through `saveEditedBytes`; the buffers live in `src/state/hexBuffers.ts`, reached through the facade `src/state/buffers.ts`.

## Tables (phase 3b)

Tables (phase 3b): a CSV is drawn by `TableView` (a window of the rows; `core/table.ts` makes `order`, never moves a row) and edited through the **text buffer**: `TableEditView` uses `loadEditorBuffer` and applies `TextChange`s from `core/csvEdit.ts` (one `isolateHistory` transaction per action) to `buffer.state`, then calls `onChanged`; never keep a second copy of the cells. The parser must be called with `spans: true` to edit. The query box is sql.js in `src/workers/sql.worker.ts` through `SqlSession`: one `SELECT`/`WITH` (`checkQuery`), `PRAGMA query_only = ON`, a worker ended after 10 s; no `eval` (AlaSQL is not an option). A `TableView` test that needs the worker mocks `@/state/sqlSession.ts`.

## Diff (phase 4)

Diff (phase 4): a comparison is a tab with `view: 'diff'` and `diff: { left, right }` (`DiffSide` = root id + path; `snapshotId` is the left root), key `diffKey`; never give it a `path`, many places read `tab.path !== undefined` as "a file" (the session skips it on purpose). Anything that follows a path (`path-changed`, `path-removed`) or a root (`root-closed`) must look at both sides: `touches` in `workspace.ts`. The two sides are read with `fb:read-file` and decoded by `core/diff.ts` (`decodeSide`: strict UTF-8, `\n` everywhere, never compared on line endings); `DiffView` makes the `MergeView` (or the unified editor) again when the files, the layout, the swap or the folding change, and only reconfigures word wrap and zoom. The choice for Compare with Selected lives in `Workbench` (`compareChosen`), not in the tree. The colours are `--wsnp-diff-*` tokens applied in `index.css` under `.fb-diff` with `!important` (merge's own light/dark rules are more specific).

## Editor groups (phase 4)

Editor groups (phase 4): at most two. `Tab.group` is absent for the left group and `1` for the right; `Workspace.active` is the tab in front of the **focused** group and `other` the one in front of the other (so code that reads `ws.active` is right for the group the user is in); every reducer path that removes or moves tabs ends in `normalize` (the second group exists only while it has tabs). `EditorGroup` is rendered once per group on `groupView(ws, group)` and `TabStrip` takes the whole `ws` plus a group (its `move` indexes are global). A view that registers itself for the whole application (`fileTarget`, `shownText`, `shownSource`) does it for its group (`useGroup()`, `createGroupSlot`) and the workbench says which group has the focus (`focusedGroup`); a new such singleton must be a group slot too. Drags (`src/workbench/dnd.ts`): the drop zone of the editor listens to the **window** (the first move of a drag counts, and a frame cannot keep the events) and a layer is drawn over each group while dragging; the tree's file drag (`FILE_DRAG`) is set for every file, and a text dropped on another text asks (`ChoiceDialog`) instead of moving, unless Shift is held.

## Editing inside a ZIP (phase 5)

Editing inside a ZIP (phase 5): `RootRegistry`'s `create`/`rename`/`move`/`copy`/`remove`/`edit`/`saveEdit` look at the path first (`zipSpot`: the **real** ZIP file through `resolveInside`, the `chain` of ZIPs inside it, the `entry`) and send a path in a ZIP to `editZip` (`core/archive/edit.ts`: one pass over the old ZIP into a temporary file next to it, `fsync`, the old ZIP looked at again, rename; the untouched entries are lazy streams, so their method, date, mode and order are kept). A ZIP that cannot be written back faithfully (ZIP64, encryption, other methods, unsafe or repeated names, over 100,000 entries) is `read-only`: refuse it before anything is written. Changes to one ZIP file go through `queued`, and every change makes the registry forget its in-memory ZIPs. An entry's `FileVersion` has a `crc32` (the entry is compared by size and CRC, never by the ZIP's date: it has two seconds of resolution, and another entry changing is not a conflict); the names of a ZIP are decoded exactly as `core/zip.ts` decodes them (`decodeName`) so the listing and the edit agree. No move or copy between the disk and a ZIP or two ZIPs (`sameZip`); an entry has no trash (`remove` with `trash` is `trash-failed`, and the interface asks for the permanent delete at once); the hex view edits only files of a folder (`edit.hexEditable`). In an e2e spec, press `F2`/`Delete` on a row you `focus()`ed, not `click()`ed: a click opens a preview tab whose editor takes the focus later and cancels the name field.

## A new text file (Untitled)

A new text file (after 0.1.2, `File ▸ New Text File`, `Ctrl+N`): a tab with `view: 'untitled'`, key `u:<n>` (`untitledKey`), `snapshotId: ''` and **no `path`**; its text is an `EditorBuffer` in `editorBuffers` made by `newUntitledBuffer` (`src/state/untitled.ts`; `saved` is the empty text, so any text is a change) and shown by `UntitledView`. Save is Save As (`saveKey` asks `edit.saveAs`; once the file is written, the new text **becomes the saved file**, see below). A comparison side for it is `{ rootId: UNTITLED_ROOT ('@untitled'), path: <tab key> }` (`core/diff.ts`), read by `DiffView` from the buffer when the tab opens, and `without()` closes the comparisons that have it; `sideOfTab`/`sideName` (`tabInfo.ts`) name a side, and `isTextTab` is true for it so the drags that ask (side by side / diff) work. It is kept between starts as a draft under the name `@untitled` (the draft handlers take `UNTITLED_ROOT` as a root; `restoreDrafts` opens `open-untitled` with the old key). Code that reads `tab.path === undefined` as "a snapshot's page" must use `isSnapshotTab` (a new text has a `view`).

The language of a new text (issue #69) comes from `detectLanguage` (`src/state/detectLanguage.ts`): it reads **only the first 64 KiB**, after a paste or a change of 20 characters or more and a **300 ms debounce** (never at every key). It **never overwrites a language the user chose** (`manual`); **Auto Detect** in the picker returns the choice to the text. The language lives in `EditorBuffer.lang` (`src/state/editors.ts`), is what `UntitledView` and the status bar read (`HTML (detected)` while it is not `manual`), and is part of the draft as the optional fields `language` and `manual` (`core/drafts.ts` drops a value of the wrong type; an older draft is plain text, not chosen). Decision functions: `nextLanguage` / `pickedLanguage` (`src/state/untitled.ts`). Tests: `src/state/detectLanguage.test.ts`, `src/state/untitled.test.ts`, `src/views/UntitledView.test.tsx`, `e2e/untitled-detect.spec.ts`.

**Save As makes the new text the file** (issue #70). After `edit.saveAs` writes the file, `saveKey` calls `convertSavedUntitled` (`src/workbench/savedUntitled.ts`), which: finds the open folder that holds the file (`rootOf`, the most specific root; a ZIP and the trash are not folders to write to) or, if none does, opens its folder as a root (the user chose that place, by the dialog); dispatches `untitled-saved` (the reducer turns the tab `u:<n>` into the tab of the file, `f:<root>:<path>`, in the same place, group and pin; if a tab of that file was open, it is the one that comes to the front and the new text's tab goes); moves the buffer with its undo history (`moveEditorBuffer`), the zoom and the chosen side of a comparison; sets the language (the extension decides; a name with none keeps the detected language; a language picked by hand stays); reads the version of the file back and marks the tab clean; and deletes the `@untitled` draft (`releaseDraft`). The next Save is then the ordinary one of a file (version check, no dialog). A name that says a picture, a video and the like opens as that kind of file (`edit.savedNotText`) and the text is let go. A cancelled or failed Save As changes nothing; if the folder cannot be opened or the file cannot be read back, the file is written and the tab stays a new text (marked saved). Known limit: if the saved file already had a tab open, the buffer it replaces shows only after the editor is mounted again. Tests: `src/workbench/savedUntitled.test.ts`, `src/state/workspace.test.ts`, `src/state/untitled.test.ts`, `e2e/untitled-save-as.spec.ts`.

## Several rows and the file clipboard

Several rows and the file clipboard (between phases 5 and 6): `ExplorerTree` keeps `marked` (a set of paths) and an `anchor` (the row clicked or reached last: where a range and a Ctrl+click start; **not** `focused`, which is already the clicked row when `click` arrives). Marks are cleared by a plain click, a plain arrow, Esc and a drag of an unmarked row, and pruned when their row leaves the screen. Every tree action takes a **list**: `move(paths, folder)`, `copyTo(paths, folder)`, `moveTo(entries)`, `remove(entries, forever)`, `paste(folder)`; `Workbench`'s `doMove`/`doCopy`/`doDelete` work through `topmost(paths)` (a folder and something in it: the folder alone), one after the other, with **one notice for a batch** (a single item keeps its own words). The drag payload `ENTRY_DRAG` has `path` (the row dragged) and `paths` (all of them). Cut/Copy/Paste is `src/workbench/fileClipboard.ts` (the app's own, module level, `useFileClip`), reached by keys (`Ctrl/⌘+X/C/V` in the tree's `onKeyDown`, left alone when there is nothing to do or the focus is in a name field) and by the DOM `copy`/`cut`/`paste` events (the macOS Edit menu roles); a cut is moved once and cleared; a clip from another root is refused (`fs.pasteOtherRoot`). `aria-selected` is the active file **or** a marked row: tests count `data-marked`. In an e2e spec press keys on a row you `focus()`ed (a click that opens a file moves the focus to its editor a moment later), and `Escape` before a key that must act on one row when marks are left.

The target of the side bar's **New File… / New Folder…** (`createRequest`) comes from the same marks (the last one, a folder or a ZIP file as itself, a file as its parent folder), else the `anchor` (the row last clicked or reached with the arrows; Esc and a click on the empty part let it go), else the folder of the active file (`activePath`), else the root — **never `focused`** (it is the last row the focus touched, and a button click does not move it). The name field says where: `placeholder` and `title` are "New folder in `<name>`" (or "New file in the root" for the root). The request is **one-shot**: `ExplorerTree` consumes it when it acts (`onCreateHandled`), `SideBar` clears it, and a remount of the tree (a switch of root via `key={root.id}`) never re-fires the same token. `SideBar` counts the tokens with its own ref, never from the request it just cleared (the next one would be 1 again and the tree would take it for the one it handled). **A click on the name of a folder or a ZIP only opens it** (never closes it; `detail` 1 of the click starts a gesture and `openedByClick` remembers that this gesture opened it); the chevron (`data-chevron`) toggles; a double click on the name closes a folder that was open before the gesture and leaves open one the first click opened; Ctrl/Shift+click only mark.

## The hex view

The hex view draws only the rows in view (a file of 4 GiB has 268 million rows: `scrollMetrics` scales the scroll) and keeps 64 KiB chunks; a bigger-than-16-MiB file of a ZIP or a snapshot is not read that way (only files of a folder), and says so with the plain card. `viewKind` answers `hex` for the extensions of programs and the like, only after a dot (a file called `bin` is still looked at as text).

## Playing video and sound

A video or a sound is played from `fb-media://<token>/`: the token comes from `fb:media-open`, which resolves a file of a root (or makes a copy of an entry of a ZIP); `MediaView`s stay mounted (hidden) so that a sound goes on playing. Do not let a `useCallback`/`useEffect` of the tree depend on a function that the side bar makes anew at every render (the tree read everything again and lost its rows).

## Open With…

Open With… hands an application a copy (entries of a ZIP) or the file; the command is run without a shell, with `Exec` parsed from the `.desktop` file; the names that could run as programs are refused (`core/stage.ts`).

## The runner

`core/run.ts` represents a command as `{ id, name, program, args: string[], timeoutMs?, cwd? }`. Arguments are never split or unquoted: each list element expands `{file}`, `{dir}` and `{name}` once and remains one argument, including quotes, spaces, newlines, shell punctuation and accents. Literal leading `-` arguments are retained exactly; `{file}` and `{dir}` must be absolute paths, so a filename beginning with `-` cannot become an option. `{name}` is the literal basename and may begin with `-`; add `--` as a separate argument when the chosen program requires it. Tilde is literal. Programs are absolute paths on the current platform or bare names searched asynchronously only in absolute, nonempty PATH directories, never in cwd. Explicit shells such as `sh -c` are permitted and shown literally in the confirmation: their interpretation is the user's choice. At most 100 uniquely identified commands, 64 arguments per command and 4 KB of UTF-8 per argument (also after expansion), without NUL. cwd is absolute or `{dir}`; timeout is optional and kills the direct child only.

`electron/run-host.ts` owns `fb:run-command`, restricted to the actual interface window's top `fb-ui://` frame. It accepts only `{ commandId, root, path }`; program and arguments always come from the main process's cached settings. Relative paths reject absolute paths, drives, NUL, backslashes and dot segments; authorised roots resolve real paths and refuse symlinks leaving the root. Disk files are handed over by absolute path; ZIP entries use `stageFile` (streamed, maximum 256 MiB, risky program names refused, mode 0400, removed on cancellation/failure or app quit). A single pending command bounds native confirmation and staging concurrency. The Open With dialog stays as strict as without commands: it stages a read-only copy of every file (disk or ZIP) and refuses risky names (`unsafe`); only the context submenu runs a command on a risky disk file. Starting uses asynchronous PATH checks and `spawn` with `shell: false`, detached, ignored stdio and `unref`; launch failures become readable results.

Before launch, the main process lazily reads at most 32 KB plus one sentinel byte of `userData/run-confirmed.json`, at most 100 id/hash pairs. Missing or malformed data grants no permission. SHA-256 hashes the fixed canonical JSON tuple of program, ordered argument templates and cwd. A native dialog shows the program and every expanded literal argument with JSON escaping and indices, and defaults to Cancel. Only Run permits launch; Always for this command atomically saves that id's current hash. Changed program/arguments/cwd require confirmation again; edits during a dialog refuse execution. Importing `files.openWithCommands` needs the settings registry's extra safety confirmation and never writes execution confirmations. Invalid/excess commands are discarded with a notice on load and an import preview warning. The Settings list editor adds, edits and removes commands; Open With and its conditional file context submenu read memory only. No confirmation file is read at startup or while opening the chooser. Performance budget: median of 20 expansions of 100 commands × 64 arguments below 10 ms; no synchronous filesystem access in launch.

## Plugin manifest

`core/plugins/manifest.ts` is an install-time pure TypeScript parser, with no Electron, IPC or startup importer. `parseManifest` accepts JSON text or plain data, validates schema 1 strictly, constructs a new object and freezes every nested object/array. Unknown fields report their path and the strict rule; failures have stable `manifest.*` codes and one-line corrective messages. Descriptors are inspected without invoking accessors; Proxies, unusual prototypes, sparse arrays and `__proto__`/`constructor`/`prototype` at any depth are refused. Text stays text. `main` is only a safe relative path and produces `hasCode`; no code runs.

Budgets: 256 KB UTF-8 JSON, depth 8 (root at 0), 20,000 nodes, 4 KB strings/list entries, 1,000 list entries/files, 100 items per contribution list and 100 configuration properties. Names/labels are 80 bytes, descriptions 500, ids 64, package paths 256. Validate 100 complete manifests in under 50 ms (median of 20); reject a 256 KB hostile JSON in under 20 ms. Import tests keep both plugins and contributions out of production startup modules; the manifest is the sole install-time consumer of contributions outside their own directory.

Commands, chords, menus and options call `validateContribution`, retaining its default 256-character/500-item/depth-5/20,000-node limits for existing callers. The manifest opts into 4,096-character strings, 1,000-item arrays and text controls; its own parser enforces byte limits first. Program/argument declarations call `parseCommandTemplate` from `core/run.ts` (64 literal arguments, no shell). Safe package paths call `safeRelative`. Reserved chords and editor language availability are checked later at installation. Activation events must reference this plugin's declared contribution; unknown code events wait for phase 3. Semver ranges support exact versions or whitespace-separated comparators only, with SemVer prerelease precedence and ignored build metadata.

Configuration accepts the six current types. `enum.values/valueLabels` map to registry `choice.choices/choiceLabels` (one locale key per value); local property keys become `<pluginId>:<key>` (already owned full keys also work). `group` becomes category, `reload` becomes restart and `sensitive` becomes safety metadata; label/description remain locale keys as text. `step`, size bounds, `order`, `scope: user`, `enabledWhen` (a comparison with a setting of the same plugin) and `renamedFrom` remain manifest metadata. No regex patterns. `key`, `folder`, `file`, `action` report `manifest.configuration.type.unsupported`, "planned for a later step". `renamedFrom` never reaches the gate. Commands use the gate's fields plus optional `keys`, `menu` and `exec`; omitted category defaults to the plugin id during validation. Menus are projected to the gate's menu items, and handlers are supplied by the future host.

`SettingsStore` already persists `plugins` as an object whose key is the entire plugin id: `plugins["a.b"]` and `plugins["a-b.c"]` are distinct; dots never create nested paths. The type contract and its snapshot document this explicitly. **o schema é a descrição estrutural para autores e ferramentas; o parser `parseManifest` é a autoridade e recusa mais**. Parser acceptance must imply schema acceptance; the reverse is not guaranteed. Runtime-only rules include uniqueness by contribution id, activation references, the `when`/chord grammar, global size/node/depth limits, UTF-8 versus character lengths, publisher/id ownership, default bounds and enum label counts, `enabledWhen` references, safe semver numeric sizes and JavaScript descriptor/prototype safety. Paths reject controls in both layers; literal `+`/`Ctrl++` chords remain valid. Keywords keep the gate's empty/whitespace strings; https URL parsing belongs to the runtime, with a case-insensitive scheme in the schema. No JSON Schema validator is installed: tests check required/allowed keys structurally and evaluate string leaves (type/length/pattern), without adding a dependency or claiming full schema execution.

## Plugin settings

`core/plugins/settings.ts` compiles the six manifest option types at install time; its only runtime import is the pure shared `core/settings/reconcile.ts` helper, which itself imports only types, and importing it never registers settings. Production startup still never imports the plugin module. Every full id belongs to `<pluginId>:` and its category is `plugins.<pluginId>`; group, order and enabledWhen are metadata for the future UI, never evaluated. Labels/descriptions/choice labels remain locale keys as text; reload maps to restart and safety is false. Installation uses the existing atomic settings contribution transaction; removal affects only this plugin's entries.

Recheck at most 100 properties, 4 KB UTF-8 strings (also list items and enum strings), 1,000 string list items, finite numeric bounds and positive steps. Numeric steps are anchored at min or zero with floating-point tolerance; no regular-expression validators. Invalid reads restore defaults with `{key, code: 'settings.value.reset'}` notices; invalid writes do not write. Cached reads use registry and store revisions, with immutable returned values. Stored plugin ids are whole keys under `plugins`, including dotted ids. Rename migration prefers the current key, drops the old key and unknown properties, and persists the repair; a changed registered type resets even when its old value fits the new type. Reset and purge are plugin-scoped; uninstall may retain data by omitting purge.

Update reconciliation keeps only declared values of unchanged type that validate, applies renamedFrom once and defaults incompatible values. The synthetic `reaches?: boolean` extension point requires confirmation when defaults, types or permitted values/bounds change. It does not extend the schema-1 parser. Portable exports include only declared valid modified values; unknown/invalid imports are skipped with preview reasons, and reaches imports always require confirmation, even for an unchanged value. Installer, UI, IPC, evaluated conditions and future option types remain later steps.

Performance tests: compile/install 50 plugins × 20 options <30 ms, read 100 options <5 ms, cached read <0.05 ms on average (median of 20 rounds). Production import scanning includes this module; no startup consumer is added.

## Plugin package

`core/plugins/package.ts` is an install-time pure TypeScript reader for folders and `.fbplugin` ZIPs. It never installs, extracts, writes, imports Electron or executes `main`. Both sources produce the same manifest and sorted verified file metadata. Hashes are computed in streams with bounded memory and asynchronous I/O between entries. `readFile` and `openStream` accept only declared verified files, enforce the file ceiling and recheck size/hash on subsequent reads; consumers of a stream must wait for successful completion before using its contents. `close` cancels active streams and releases the ZIP. A mutable folder is not a snapshot: installation must handle final atomic staging in step 2.3.

Names call `safeRelative` without accepting its sanitization. Refuse traversal, absolute paths, backslashes, NUL/controls, empty components, reserved Windows names, trailing dots/spaces, duplicates and case/NFC collisions (including implicit parent directories), file/directory conflicts, symlinks and hardlinks, special files, encrypted entries and unsupported compression. All files except the root manifest and signature must be declared and present, with matching SHA-256; PNG icons need the eight-byte magic, SVG is refused, and level 0 refuses executable/script extensions. `main` is declared hashed data, never executed.

`SIGNATURE` is the optional strict Ed25519 record described in Extensions Design §3, covering the exact manifest bytes. A present invalid signature is refused, a missing/mismatching publisher key is `package.signature.key-mismatch`, and a missing signature gives `{ signed: false }`. Fingerprints reuse `fingerprintOf`; raw public keys use the standard Ed25519 DER/SPKI wrapper and `node:crypto.verify`. Pure `trustLabel` consults only `SignerStore.isTrusted`: catalog origin, then trusted/unknown valid signer, then unsigned repository, then unsigned. The reader never labels a folder as catalog, even if passed that origin.

`PluginPackage` exposes the exact verified `manifestBytes` (at most 256 KiB) and optional `signatureBytes` (at most 4 KiB) without reserialization or additional copies; their properties cannot be reassigned. Node Buffers cannot be frozen: consumers must treat their contents as read-only.

`PACKAGE_LIMITS` caps total inflation at 50 MiB, central/directory entries at 2,000 (directories count to bound metadata), individual files at 16 MiB, the manifest at 256 KiB, expansion at 100:1 per entry and overall, components at 255 characters, paths at 1,024 and directory depth at 16. Options may only reduce positive finite ceilings; manifest parser ceilings remain independently enforced. Count actual decompression bytes and abort on excess, rather than trusting header sizes; header oversize is refused before inflation. Errors use stable `package.<area>.<rule>` codes, with manifest errors prefixed `package.`.

## Installing plugins

`core/plugins/install.ts` receives the plugin root; it imports no Electron and executes no plugin. Layout: `<root>/<id>/<version>/`, `.staging/<random>/`, and `installed.json`. All paths are checked against the root and link components are refused, including a symlink root. Installation streams verified package files, rechecks sizes and SHA-256 while writing, yields between files, and writes the exact manifest/signature bytes. Files are synced and made read-only (0444, directories 0555 on POSIX; supported read-only permissions on Windows). The top staging directory temporarily needs write permission to move its `..` entry between parents; 0555 is restored before publishing the index.

The schema-1 index is the only file read on ordinary startup: strict fresh records, 1 MiB ceiling, frozen cache by mtime/size, and a same-directory temporary file with fsync and rename. Invalid indices are quarantined as `installed.json.bad-<time>-<random>` and rebuilt from reparsed installed manifests; rebuilt plugins are disabled and `install.index.rebuilt` warns the caller. Recovery does not infer signature trust. Installation publishes the version directory before the index; failure before index publication removes that new version and preserves the active record. An update preserves enabled and keeps one previous version. The obsolete version is moved into staging before index publication and restored if that publication fails. Its final cleanup failures after commit are returned as `install.cleanup.failed` warnings; the visible id folder still retains at most the active and previous versions.

Rollback verifies the retained package, swaps active/previous and refreshes metadata; a signed retained package is conservatively labelled signed-unknown because the installer has no signer store. Uninstall moves the id folder into staging, publishes index removal, then makes files writable and removes them; settings purging belongs to the caller. Enable/disable only rewrite the index; Disable All uses one rename. Mutations and recovery are serialized by an in-process promise queue per canonical root (`realpath` of the created root, so two spellings of one folder share it), with no disk locks. A version directory that the index does not record (a crash between the rename and the index, or a lost index; a missing index reads as empty) is an orphan: install removes it and installs; a version the index records as previous is reused only with identical manifest bytes (`install.version.exists` otherwise). Links found in `.staging` or inside a plugin are removed without being followed or chmod-ed; uninstall and cleanup always finish. Only install (or explicit maintenance) cleans staging older than one hour; ordinary startup does not scan installed versions or staging.

Budgets enforced by synthetic tests: 5 MB/200 files installed under 800 ms, 5 ms timer gaps under 50 ms, absolute heap peak under 40 MB in a fresh Node isolate, 100-record index under 5 ms (cached read under 0.5 ms, median of 7 rounds of 100 calls), and 200-file uninstall under 300 ms. Reference medians of 3 runs under load: 210 ms, 6.5 ms, 13.5 MB, 3.4 ms, 0.077 ms, 24 ms. No new dependency.

## Contributions

`core/contributions/` is a pure TypeScript install-time gate, with no Electron or renderer dependency and no production startup importer. `contract.ts` is the standalone, documented type source of the future `.d.ts`; its declaration text and exported names are snapshot-tested. `Contribution` contains `pluginId` and optional commands, keys, settings and menu items. Handlers come separately from the trusted host, never from manifest data. Command declarations cannot hide keys or menus in extra fields.

Validation constructs new bounded plain data: at most 500 entries combined, 256 characters per string, depth 5 and 20,000 data nodes; unknown fields, accessors, inherited objects, sparse arrays and `__proto__`/`constructor`/`prototype` are refused. Plugin ids are lowercase identifiers; every command/option/menu id and command reference uses exactly `<pluginId>:<name>`. No core id can be claimed. Settings reuse the six registry types and persist through `SettingsStore` under `plugins.<id>`.

Application validates every declaration, handler, reference, duplicate and reserved chord before writing. A settings transaction suppresses intermediate notifications and restores entries/revision on failure. Each command/key/menu undo is armed before its writer, including writers that insert and then throw. Successful application returns an immutable handle of installed ids and conflicts; a second application of the plugin is refused. Removal drops all installed entries owned by that plugin and is idempotent. The existing settings batch API now uses the same transaction.

The user keeps priority over plugin defaults. Reserved chords are rejected for both platforms and reject the whole contribution. A collision with an existing core, user or earlier plugin key is reported in the handle and the incoming plugin key loses; no existing binding is overwritten. Commands retain their compiled `when`; menu conditions use the same grammar.

Menubar destinations are `menubar/file`, `menubar/edit`, `menubar/view`, `menubar/go`, `menubar/tools`, `menubar/help`. Items are projected after existing entries, sorted by group, declared numeric order, then id (locale-independent). With no contributed items the exact original menu array is returned. Current `MENUS` has five headers and no Tools: `menubar/tools` is a dormant contract destination, not a new visible header. `context/tree`, `context/tab`, `context/editor` are reserved in the type but explicitly rejected until implemented. Nothing calls this gate at startup; a test scans imports/re-exports/dynamic imports in all production `src/`, `electron/` and other `core/` modules. Existing menu golden tests and their snapshots must remain unchanged.

Budget: exactly 500 entries applied and removed in under 100 ms each (median of 20; measured about 2 ms and 1 ms), bounded data, install time only. Synthetic acceptance tests use the actual registries; `mutations.test.ts` runs mutated copies of the sources (prevalidation, rollback, prefixes, reserved chords, full removal, built-in menus, ordering) and expects each to be caught.

## Command registry

`core/commands/` is pure TypeScript data and logic: core ids have no colon; namespaced plugin ids use `<plugin-id>:<name>`. `CommandDef` is the shared source for a command's translation key, category, optional compiled `when`, default key chords and menu/palette placement. Menus, palette entries and native menu command ids are derived from the built-in registry; the palette constructs command items only while open. Preserve the current labels, order, groups, shortcuts and disabled states. `when` supports boolean keys, `!`, `&&`, `||`, parentheses, and string equality/inequality; parse once at registration, evaluate only own context properties, and never use `eval` or `new Function`. Handler maps are keyed by the command id union so every built-in handler is checked at compile time. Golden and registry-equivalence tests protect the visible menu data.

## Key table

`core/keys/` builds a Map of normalized chord → all command ids from `builtinKeyCommands`, derived from the registry's `keys`. Its legacy menu spelling `Ctrl` means `Mod`; explicit Control navigation and platform-specific tab defaults are data in `builtin.ts`. `Mod` is Command on macOS and Control elsewhere; `mac:` and `nonmac:` qualify defaults. Chords normalize modifier order, arrow aliases and letter case; events retain named-key case and all modifiers exactly as the frozen dispatcher did. Literal plus is `Mod++` or `Mod+Plus`; Shift is explicit. Invalid chords throw a clear error.

Ambiguous bindings retain every id; resolve `when` only in the window. `commandFor` and native accelerators forward only unambiguous bindings; Copy stays with the focused editor/page. Removal preserves other ids on the chord. Display shortcuts and native accelerators share the formatter, with unchanged menu/palette golden snapshots. Budgets: construction below 2 ms, 100,000 event lookups below 100 ms (median of five); no per-event parsing or IPC is added.

Plugins must pass `assertPluginChord`. `reserved.ts` documents the exact platform-qualified list: all built-in chords (including zoom, navigation and tabs); Mod+C/X/V/A/Z and Mod+Shift+Z, Ctrl+Y off macOS; Mod+Q, macOS Mod+H/Mod+Alt+H/Ctrl+Mod+F, Alt+F4 and F11; arrows/Home/End/PageUp/PageDown and Shift selection, Control word/document movement, macOS Alt word and Command line/document movement; Backspace/Delete and word deletion, Enter, Tab/Shift+Tab and Escape. It also protects the `defaultKeymap`/`historyKeymap` installed by `src/views/codeTheme.ts`: Alt+Up/Down and Shift+Alt+Up/Down, Mod+Enter, Mod+/, Mod+Alt+backslash, Mod+D, Ctrl+M, Alt+L, Ctrl+I, Mod+Shift+K, Ctrl+Shift+Z, and macOS Control editing aliases B/F/P/N/A/E/H/D/K/O/T/V/Shift+V. Unknown valid chords remain available. This step provides the guard; plugin installation is later work.

## User keys

`keybindings.json` sits in the application's own folder (`app.getPath('userData')`: `~/.config/folder-browser` on Linux, `%APPDATA%\folder-browser` on Windows, `~/Library/Application Support/folder-browser` on macOS), next to `settings.json`. It is optional: nothing creates it, so without it the keys, menus, golden tests and the key oracle are exactly the built-in ones. Format (VS Code's): a JSON list of `{ "key": "Mod+Alt+J", "command": "<id>", "when"?: "<expression>" }`; `{ "key": "Mod+B", "command": "-<id>" }` removes the built-in key of `<id>` on that chord (a removal takes no `when`, and may name a built-in chord). `core/keys/user.ts` validates **entry by entry**: an invalid chord, an unknown command id, a `when` that does not compile, or a new key on a reserved chord (`reserved.ts`) is dropped with a warning that names the entry, and the rest of the file is used; a file that is not a list, is not JSON or is over 256 KB gives only the built-in keys and one warning. The file is never rewritten because it is invalid.

`mergeUserKeys(commands, entries, mac)` returns the effective table (`lookup`, `get`, `shortcut`, `accelerator`, as the built-in table has), the **conflicts** (the same chord on different commands whose `when` do not provably exclude one another: only conjunctions of booleans, `!` and string comparisons are proved; anything else is listed as a conflict) and the warnings. A user key for the same command and `when` replaces the older one; the user's key is what menus and the palette show. Budget: 500 entries merge in under 10 ms (median of 20, `core/keys/user.test.ts`).

Both processes read the file. `electron/keys-host.ts` reads it once at start, synchronously and bounded to 256 KB + 1 byte (a missing file costs one `existsSync`, no read, no `stat`, no table); it watches the folder and, 200 ms after a change, creation or removal of `keybindings.json`, rereads it (bounded) and broadcasts `fb:keys-changed` (and, on macOS, rebuilds the native menu). `fb:keys-get` is synchronous and read once by the preload, whose copy `window.fb.keys.get()` is refreshed by `fb:keys-changed`; `fb:keys-set` takes a list validated as `unknown`, refuses any warning, and writes atomically and in order (`atomicWrite` of `settings-host.ts`); it is used by the Settings ▸ Keyboard panel. Every channel answers only the interface's own top frame.

Settings ▸ Keyboard lists every registered command with translated title/category, effective key and Modified mark. Search by title, id or key is deferred; Show Only Modified combines with it. Pagination mounts at most 40 rows, with focusable rows and native buttons. Budgets: 500 commands filter below 10 ms and the panel opens below 200 ms (`src/views/KeyboardPanel.test.tsx`). Record key announces its state, captures one nonmodifier chord using the core formatter, ignores repeats/composition, and cancels on Escape or window blur. Reserved chords are refused immediately with a reason. Before confirmation the core merge reports conflicts whose `when` clauses do not prove separation. Recording temporarily suspends the main shortcut bridge and native menu accelerators for that window (`fb:keys-recording`, synchronous, validated boolean/top frame); cleanup resumes them, also when the interface reloads or crashes (`did-navigate`, `render-process-gone`) or the window closes. The recorder is a layout effect whose dependencies are only the command being recorded: a reread of `keybindings.json` or a change of language must not restart it (a restart let the native shortcuts back for a moment and lost the chord; `src/views/KeyboardPanel.test.tsx`, `e2e/keyboard-panel.spec.ts` ask the real `before-input-event` bridge). Replacing/removing a key emits removals for all platform defaults; Reset deletes both additions and removals for that command, including hidden/conditional entries. Reset All requires a UI confirmation. `fb:keys-set` is now invoked and returns `{ok, warnings}` after the serialized atomic write.

Keyboard Export/Import reuse the settings JSON dialogs, bounded asynchronous reader and atomic writer. Paths are selected only in the main process; no renderer path is accepted. Import reads at most 256 KB plus a sentinel byte, rejects structural errors, previews valid entries, skipped warnings and conflicts, and replaces user entries only after Apply. The main process owns one preview per sender; apply requires its token and an explicit true confirmation, consumes it, and refuses stale current bindings. Cancellation of a new chooser invalidates the prior preview. `fb:keys-export`, `fb:keys-import-preview` and `fb:keys-import-apply` validate unknown arguments and restrict senders to the interface top frame. No filesystem work or IPC per row runs during filtering.

**The snapshot frame rule.** A snapshot's frame never lets the interface see a key, so a user key reaches the window only if the main process forwards it in `before-input-event`, from the same effective table (`setUserKeys` in `core/keys/effective.ts`, set by the host). The main process has no window context, so it forwards **only unambiguous chords with no `when`**; a key with a `when` is decided in the window (`commandFor(event, mac, context)`) and therefore does not work while a snapshot's frame has the focus. `e2e/user-keys.spec.ts` proves, with the focus inside the frame of a `.wsnp`, that a user key acts, that a removed built-in key does nothing, and that a file edited on disk is read again. (The spec sends keys with `webContents.sendInputEvent`: Playwright's keyboard goes through DevTools and never passes `before-input-event`.)

## Gotchas inherited from wsnp-viewer

- A hidden view must be created with `offscreen: true` to be photographed. Closing the last hidden window must not quit the app (`window-all-closed`).
- yauzl closes the file itself when the last stream ends: never `closeSync` a descriptor yauzl opened. ZIP64, ZIP encryption and methods other than stored/deflate are refused (so such a ZIP is read-only).
- The interface may import from `core/` only types and pure modules (`@core/…`): importing `core/validate/index.ts` would bundle Node modules into the renderer (use `core/validate/issues.ts`).
- PDFs are drawn by pdf.js in the interface: the build copies its data into `dist/pdfjs/` (`vite.config.ts`), the CSP allows `worker-src 'self'` and `'wasm-unsafe-eval'`, and the `fb-ui` scheme needs `supportFetchAPI`.
- Extraction goes through `safeRelative` and `extractEntries` (never write a ZIP name as it is). The interface keeps no ZIP: the main process holds the last two in memory.
- Find and Copy act on the tab on screen: the page of a snapshot is another process (`fb:page-find`, `fb:page-copy`); a menu press must not move the selection (`onMouseDown` preventDefault); do not give the `FindBar` a `key`.
- An effect must return nothing or a function: `useEffect(() => node?.scrollIntoView?.())` returns what `scrollIntoView` returns and React calls it as the clean-up; write the body in braces.
- A ZIP saved by PageKeep opens converted into a temporary `.wsnp` (`OpenSnapshot.file`; `path` stays the ZIP's).
- Right clicks in the page of a snapshot reach the main process as `context-menu` and are drawn by the interface (`fb:page-context`).
- Linux **Open With…** is our own dialog (`OpenWithDialog`, `core/apps.ts`, `electron/open-with.ts`): the desktop's chooser opens behind the window on Wayland. The e2e tests give `gio` a made-up desktop through `XDG_DATA_HOME`, `XDG_DATA_DIRS`, `XDG_CONFIG_HOME`.
- **Zoom is per tab**: never zoom the window. The wheel and zoom keys inside a snapshot reach the interface only through `core/frameScript.ts`.
- An `<iframe>` moved in the DOM reloads: the snapshot frames keep the order the snapshots were opened in.
- Electron has no DevTools `Page.printToPDF`: use `webContents.printToPDF`.
- `::highlight()` makes Vite print two CSS warnings: harmless.
- Details of the inherited design and its measurements: `docs/WSNP-VIEWER-ARCHITECTURE.md`; the history: `docs/WSNP-VIEWER-HISTORY.md`.
