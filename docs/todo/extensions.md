## Extensions (plugins): a safe system, side load and an online catalog (after 0.1.3; priority Later, after the registries it needs)
Idea, decided in principle: **security comes first**; the design, the package format, the trust chain, the catalog and the threat model are in [`docs/EXTENSIONS-DESIGN.md`](../EXTENSIONS-DESIGN.md) (a sketch, read it before the work). In short: **level 0** extensions are **data** (themes, key schemes, language packs, file type to language, snippets, Open With entries and commands the *application* runs after a confirmation): validated, never run; **level 1** extensions have **code in a box** (a worker, a sandboxed frame or a WebAssembly module: no Node, no IPC, no network, a brokered API with permissions that are denied by default); **level 2** extensions (Node code in a **process of its own**, with enforced permissions where the platform can, or **full trust** behind a typed confirmation) are **also planned, last, off by default**: the aim is that **every level is supported**. Packages are `.fbplugin` files (a ZIP with a manifest and a signature) installed **from a file (side load)** or from an **online catalog that the user turns on** (a signed static index in a public repository: nothing leaves the computer unless the user chose it). The foundations come first: the **settings registry**, a **command registry**, the **editable key table** and the **Open With custom command** (each useful alone; the extension system is built on them, and some of the application's own features are made **through the same extension points** to prove the API).

Phase 1: the package, side load and level 0 (priority Later; size L)
- [ ] **The command registry and the contribution points** inside the application (themes, key schemes, languages, commands, menu entries, Open With entries, locales, snippets), each a typed registry that the built-in features also use; the manifest **JSON Schema** (`schema: 1`) and a validator that builds a **new, strict object** from the JSON (size and depth limits, no prototype pollution, strings kept as text)
- [ ] **The package reader** (`core/extensions/package.ts`, plain TypeScript, no Electron): the limits on size, files, ratio and names (`safeRelative`), no symbolic links, no executables or scripts in level 0, the **file hashes** checked against the manifest, the **ed25519 signature** (the code of `core/validate/signature.ts` and the store of trusted signers `core/signers.ts` are reused) and the trust label (**Reviewed**, **Signed by a publisher you trust**, **Signed, unknown publisher**, **Unsigned**); a fuzz and bomb corpus in `fixtures/hostile.ts`
- [ ] **Install and remove**: File ▸ **Install Extension from File…**, drop a `.fbplugin` on the Extensions page; the **install screen** (name, publisher and **key fingerprint**, version, what it contributes, what it asks for, size, source and trust label; a second confirmation unless it is Reviewed); an **atomic** unpack to `userData/extensions/<id>/<version>/` (read-only), a small `installed.json` index (the only thing read at start), a **rollback** to the previous version, and **uninstall** that removes the folder and its data
- [ ] **The Extensions page** in Settings (see "Settings"): Installed (enable and disable, version, publisher, trust label, what it contributes, permissions granted, size, a log, **Open its folder**, remove), Browse (online, off until turned on), Updates, **Disable All**, and **safe mode** (a menu item and a `--safe-mode` flag, offered after a crash at start)
- [ ] **Level 0 contributions working**: themes (colour tokens, with a preview and a reset to the built-in theme), key schemes (with the **reserved keys** an extension cannot bind: `Ctrl+S`, `Ctrl+W`, `Delete`…), language packs and file-type to language, snippets, **Open With entries and commands** (a program and arguments with `{file}` as **one** argument, run **by the application without a shell**, shown at install and **confirmed again on the first run**), and menu entries that call those commands; **developer mode** (an unpacked folder, reloaded on change, a banner while on, off by default)
- [ ] **Settings of an extension** (`contributes.configuration`, see `docs/EXTENSIONS-DESIGN.md` section 3b): declared in the manifest (types `boolean`, `enum`, `number`, `string`, `colour`, `list`, `key`, `folder`, `file`, `action`; a default, a label and description as locale keys, `group`, `order`, `keywords`, `enabledWhen`, `reload`; **at most 100 per extension, strings 4 KB, lists 1,000 items, no regular-expression patterns**) and **made into entries of the settings registry at install**, so they are listed, searched, validated, stored, reset, exported and imported by the Settings page **with no extension code running**: **Settings ▸ Extensions ▸ <name>**, a **Settings** button on the card, **Reset all of this extension**, a disabled extension's options shown greyed; stored by the application in `settings.json` under `extensions.<id>`, **validated on every write and read** (a stored value that no longer fits falls back to the default with a notice), with a declared **`renamedFrom`** for a renamed option and the unknown keys dropped on update; **uninstall asks** whether to keep or delete them; level 0 contributions can use an option (`{setting:contrast}`) as **one validated argument**, never glued into a command string; an option that **widens what the extension may reach** is never kept silently across an update nor taken from an import without the user's confirmation; `sensitive` options (secrets) are **not offered** until a network permission exists (then kept with `safeStorage`, never exported)
- [ ] **Compiled at install**: contributions go into the registries when the extension is installed, so **start-up reads one small index** and nothing else, nothing is activated until its `activation` event (a file type opened, a command run, a theme chosen); a budget: the start of the application is **not slower** with 50 level 0 extensions installed
- [ ] The author's tools: a **validator and packer** script (`scripts/fb-extension.mjs`: validate, pack, sign, verify, all offline), `docs/EXTENSIONS.md` (how to write a level 0 extension), and **three examples** (a theme, a key scheme such as Notepad++'s, a Spanish language pack)
- [ ] Tests: the manifest schema (good, missing field, wrong type, huge, deep, `__proto__`); the package reader against every hostile case of the threat model; trust labels; install, update, rollback and uninstall; the permission-difference refusal; a theme and a key scheme applied and removed; reserved keys refused; an Open With command run with an argument that has quotes, `$`, `&` and a leading `-` (no shell, one argument); safe mode; and an end-to-end spec (install a package from a file, see its theme, restart, disable it, remove it)

Phase 2: the online catalog (priority Later; size M to L; needs phase 1)
- [ ] **The catalog client** (opt-in, off by default, explained in plain words in Settings ▸ Privacy ▸ Extensions: one HTTPS read of a small index, no identifier, the host sees the IP address): fetches `index.json`, its signature and `revoked.json` **only when the Browse page opens or Check for Updates is pressed** (never at start, never in the background); `ETag` caching; a fixed `User-Agent`; the **catalog's public key is in the application** (and a second for rotation); an index is accepted only if its **signature verifies**, its **`sequence` is not lower** than the last seen and it is **not stale** (rollback and freeze attacks); a **download only on a click**, checked against the entry's **pinned SHA-256**, then the package's own signature and file hashes, then the install screen
- [ ] **Browse**: the list from the signed index (name, summary, publisher, level, categories, permissions in a line, size, **Reviewed** mark, an icon loaded lazily and only after the click on the entry), a **search** and category filter on the index already in memory (no request per keystroke); **Install**, and **Updates** that are **offered, never applied**, with the **permission difference** shown and accepted again when it grew
- [ ] **Revocation**: the signed blocklist disables an installed extension or a publisher key **at once**, with a notice that says why; without the catalog turned on the application cannot know, and the page says so
- [ ] **Air gap and mirrors**: **Browse a catalog from a folder** (an `index.json`, its signature and the packages beside it); a mirror is only a cache and still needs **the catalog key's signature**; another catalog key is a **developer-mode** setting, never a default; installing from a URL typed by the user is **not** offered
- [ ] **The repository side** (`folder-browser-extensions`, a public repository, a static site): the layout of `index.json`, `revoked.json` and their signatures, a **pull request flow** for authors, **CI** that validates the schema, sizes, hashes, that a level 0 package has no code, that the permissions match the description, the **publisher namespace rule** (the id must match the account or organisation that owns the package's repository: against impersonation and typosquatting), and the hostile-package tests; a **human review** for level 1 and for any growth of permissions; the **signing of each publication offline** with the catalog key on a hardware token (never on CI); `docs/EXTENSIONS-POLICY.md` (what may be published, how to report a malicious one, **takedown and revocation** with a time target, key rotation and a leaked publisher key, the API stability promise)
- [ ] Tests: a fake catalog server for every case (a bad signature, an older `sequence`, a stale index, a hash that does not match the entry, a package signed by another key, a revoked extension and key, a mirror with the wrong key, a download that is cut off, a huge index); the page's states (off, offline, loading, the list, an error in plain words); the permission-difference screen; and an end-to-end spec against a local fake catalog (browse, install, update offered, revoke). Performance: the index is small and gzipped, sharded by id prefix when it passes a limit, parsed off the interface's thread, and held in memory only while the page is open

Phase 2b: the distribution channel for extensions (priority Later, with phase 2; size M; an infrastructure and operations job more than code)
The catalog of phase 2 is **the channel**: this phase makes it a real, reachable and operated service. It stays **static, with no accounts and no server code** (nothing to break into, nothing to run), and **the trust is in the signatures, not in the host**, so it can be mirrored anywhere.
- [ ] **The catalog repository** (`folder-browser-extensions`, public, under the same organisation, with its own `README`, `CONTRIBUTING`, `SECURITY` and issue templates): the layout of `catalog/v1/` (`index.json`, `index.json.sig`, `revoked.json`, `revoked.json.sig`, `icons/`), a **pull request template** for a new extension and for an update, the **CI** that validates it, and a protected `main` that only the maintainers can merge to
- [ ] **Hosting and mirrors**: published as static pages (GitHub Pages first), with the **same files mirrored** to a second host (so a single outage or a takedown does not end the channel) and **listed in the application** as the default and a fallback; the packages are **release assets** of each author's repository (or of the catalog's for a first-party extension), each pinned by its SHA-256 in the signed index; **rate and size limits** on the index (sharded by id prefix past a limit)
- [ ] **The public page of the catalog** on the site (`docs/todo/positioning.md`, "A site"): a browsable, searchable list **generated from `index.json`** (name, summary, publisher, level, permissions, size, the **Reviewed** mark, versions and their changelogs, the publisher's key fingerprint), with a **permalink per extension**, a **Report** link, and an **Install** button that opens the application (a `folder-browser://extension/<id>` link that shows the install screen: it **never installs by itself**)
- [ ] **Publishing made easy and safe**: `fb-extension publish` (see "Phase 5") prepares the package, signs it, checks it against the conformance list and **opens the pull request** on the author's behalf; first-party extensions are published by the same flow from this repository
- [ ] **Operations**: the **offline signing ceremony** for each publication (the catalog key on a hardware token, two maintainers for a level 2 or a permission change, a signed `sequence`), the **key rotation** and **leaked-key** procedures rehearsed, an **abuse report** channel with a **time target for takedown and revocation** (a signed `revoked.json` published within hours), a **transparency log** (every publication, removal and revocation is a commit in the public repository) and a **status page** (what the catalog's last `sequence` and date are)
- [ ] **Policy and moderation**: `docs/EXTENSIONS-POLICY.md` (what may be published, the review criteria by level, namespaces, takedown, appeals, what the reviewers do and do not promise), a **review checklist** per level, and a **code of conduct**
- [ ] **Later options, not now**: **publisher verification** beyond the GitHub namespace rule; **ratings or comments** (not planned: they need accounts and moderation); **paid extensions** (not planned); a **private catalog** for a company (the air-gap and mirror path already covers it, with its own key in developer mode)
- [ ] **Performance and tests**: the client costs one small request on demand (see phase 2); the site is static and cached; tests of the CI rules with hostile submissions (a typosquat, a level 0 package with code, a permission that grows, an id that belongs to another owner, a bad signature, a duplicate version), and a **dry-run of the whole publication** (sign, publish to a staging copy, install from it in an end-to-end spec) before every real one
- **Decisions to make**: where the catalog and its mirror live; **who holds the catalog key** and the second key for rotation (one maintainer, or two with a threshold); the **time target** for a takedown; whether the first-party extensions live in the catalog's repository or in this one; and whether the `folder-browser://` link is accepted in version 1

Phase 3: level 1 (priority Later, after phase 2 is in use; size L; one extension point at a time)
- [ ] **Reading the options from code**: `settings.get`, `settings.getAll` and `settings.onChange` (debounced, batched, only the keys that changed) on the broker; an extension reads **only its own** options and writes them **only** through a declared `action` or a UI of its own that goes through the same validation; an option with `reload` restarts the extension when it changes
- [ ] **The host API and its broker**: a message channel (`{ id, method, params }`) from a worker or a sandboxed frame to the main process that is the **only door**: each call checked against the manifest's **granted** permissions, **validated as untrusted input** (`unknown`), rate-limited, quota-limited (wall time, CPU share, memory, messages), answered, and **logged in an activity log the user can read** (which files an extension read and when); versioned (`api: 1`) with a **stability and deprecation promise**; **no direct IPC and no Node** in any extension context
- [ ] **Permissions** as in the design (`files.read` per open root and read-only, `ui.panel`, `ui.statusItem`, `ui.viewer:<ext>`, `commands`, `clipboard.write` after a gesture, `storage` with a quota); **none granted by installing**, shown by name at install and when they grow, revocable later; **`network`, `files.write` and `process` are not offered in version 1**
- [ ] **Where the code runs**: a **Web Worker** (pure logic: a converter, a reader of a format), a **sandboxed frame** with an opaque origin served by `fb-ext://<id>/` with a CSP per extension and every other request cancelled (a panel or a viewer, labelled with its name and a "from an extension" mark so it cannot pass for the application's own dialog), and a **WebAssembly module** that is checked to import **only** the host functions of the broker (a reader of 7z, a decoder of AC3, an image codec as an extension: the plans for "Archives" and "Video" can use this instead of shipping binaries)
- [ ] **Extension points, one by one**, each with its tests and its example: commands that compute on the selection or the text (the "Text tools" as the first, **built through the same point**), **viewers** for a file type, **exporters and converters**, **metadata readers**, **status bar items**, **side panels**; a point is added only when a built-in feature has used it
- [ ] **Quotas and the kill switch**: a runaway or crashing extension is stopped and marked, with a notice, and never takes the window down; a **safe mode** that disables all; a **review gate**: level 1 is **never** shown as Reviewed without a human review, and unsigned level 1 is never installable
- [ ] Tests: every row of the threat model as a test (an extension that tries a path outside its root, a `..`, a symlink, `fetch`, a WebSocket, an image to a remote host, `postMessage` to the parent with a forged id, a busy loop, a memory bomb, a prototype-pollution payload, a UI that imitates a dialog, a key hijack, a command with a shell string); the broker's validation fuzzed; the isolation checked as data (the frame's `sandbox` attribute and CSP); a budget: a call through the broker adds under a millisecond and a started extension does not slow the typing in the editor

Phase 4: level 2, extensions that run as a process (priority Later, after phase 3; size L; **built last and most carefully**)
- [ ] **A spike first, with its findings written in `docs/EXTENSIONS-DESIGN.md`**: which of Node's **permission model** flags (`--permission`, `--allow-fs-read`, `--allow-fs-write`, no child process, no worker, no addons, no WASI) an Electron `utilityProcess` accepts and **enforces** on Linux, Windows and macOS, how it behaves with symlinks and with a path that is a different spelling of an allowed one, what an **OS-level sandbox** can add (seccomp or AppArmor on Linux, a job object on Windows, the App Sandbox on macOS), and what must be **refused where it cannot be enforced**
- [ ] **The setting**: Settings ▸ Extensions ▸ **Allow extensions that run as a process**, off by default, with a plain warning; a level 2 package cannot be enabled while it is off, and **a settings import, an update or a package can never turn it on**
- [ ] **The runtime**: a `utilityProcess` per extension, started on activation and stopped when idle, with **no `window.fb`, no interface IPC**; a **message port to the broker** (the same validated, rate-limited, logged API as level 1, plus the level 2 methods the extension points need); a **restart** button and a notice on a crash or a hang; **quotas** on memory and CPU time; the data folder `userData/extension-data/<id>/` with a quota
- [ ] **Restricted mode** (`"trust": "sandboxed"`): the process started with the **allow-lists made from the granted permissions** (folders to read, folders to write, `network:<host>`), **no child processes, no worker threads, no native addons, no network** unless granted; permissions shown **by name and by folder** at install, **grown permissions refused until accepted again**, revocable at any time; offered only on a system where the spike showed it holds
- [ ] **Unrestricted mode** (`"trust": "full"`): only with a **signature**, a **typed confirmation** that names the extension and the publisher's fingerprint, never installable by a drag, a double click, an import or an update **without that confirmation**, a **permanent mark in the status bar** while any is enabled, **off in safe mode**, the **Full trust** label in red beside its name everywhere it is listed
- [ ] **Catalog rules for level 2**: its own section with the warning, **never Reviewed without a human security review** of the source and an inspectable or reproducible build, a pinned hash, no obfuscation, a reachable publisher; **revocation** disables it and **kills the process** at once; the CI of the catalog refuses a level 2 entry with no review record
- [ ] **Extension points that need it**: a **helper program** an archive or video extension ships per system (hash-pinned, in the package, run from the installed read-only copy only), a **language server**-like service, a converter that starts a tool the user has; each declared in the manifest, each shown at install
- [ ] Tests: the permission model's allow-list **checked as data and by an attack** (an extension that reads `/etc/passwd`, writes outside its folder, follows a symlink out, spawns `sh`, loads a `.node` file, opens a socket: all fail in restricted mode); the unrestricted flow's confirmation (wrong text refused, no way around by drag or import); the setting off refusing to enable; a crash, a hang and a memory bomb contained; the kill on revocation; and an end-to-end spec with a made-up level 2 extension. Performance: a level 2 process costs nothing until activated, and a call through the broker stays under a few milliseconds
- The **security scan** (`/claude-security`, only when the user asks) of the process host and the broker before this phase ships

Phase 5: the authoring guide and kit (priority Later; written **after phases 1 to 3 are implemented**, so it describes what exists; size M)
- [ ] **`docs/EXTENSIONS.md`**, the one document a programmer **or an AI agent** reads to make an extension (the outline is in `docs/EXTENSIONS-DESIGN.md`, section 10): start here and the five-minute path, the manifest field by field, the host API reference per level (**generated from the TypeScript types** so it cannot drift), recipes, the security rules as a checklist, testing, publishing, and a chapter for agents; in English and Brazilian Portuguese
- [ ] **Recipes for settings** in the guide (an enum, a number with a range, a folder, an action, `enabledWhen`, a rename across versions, reacting to `onChange`) and the **settings schema** among the JSON Schemas; **JSON Schemas** (`docs/schema/*.json`) for the manifest, the catalog index and the blocklist, used by the validator, the catalog CI and any tool; the guide's examples are **run by a test** (a broken example fails the build)
- [ ] **The `fb-extension` tool** (`init`, `validate`, `pack`, `sign`, `verify`, `test`, `docs`), offline, with **`--json` output and stable error codes** (each with a one-line fix) so an agent can loop on it; the **test host** (a fake broker, a virtual file system, a clock, budgets for activation, memory and call latency)
- [ ] **For agents**: `AGENTS.md` in every template (what to read first, the commands, the definition of done, the rules: never request an unused permission, never fetch or evaluate code at run time, stop and ask the person before publishing), an `llms.txt`-style index of the guide, and the **conformance checklist** that the catalog's CI runs, runnable locally first
- [ ] **Templates**: one repository per kind (theme, key scheme, language pack, command, viewer, WebAssembly converter, process tool) with tests, a `README` and a release workflow that builds, packs and signs reproducibly
- [ ] Tests: a sample extension of each kind is built from its template by CI and installed in an end-to-end spec; the guide's code blocks run; the schemas accept every example and reject the hostile ones; `fb-extension validate --json` gives the same codes the install screen shows

Performance and security (a requirement of every phase, per the rule at the top)
- [ ] The start of the application does not wait for extensions (a small index, activation on demand, contributions compiled at install); the catalog fetch is background, small and cancellable; quotas bound every extension; the **activity log and the permissions page** are the user's way to see what an extension does; the **security scan** (`/claude-security`, when the user asks, see "Light use" in `CLAUDE.md`) is run on the extension host and the package reader before each phase is released

Decisions to make before this is started
- **The order**: the registries and the Settings framework first (as the roadmap says), then phase 1; is that right, or should themes and key schemes as extensions come sooner?
- **Where the catalog lives**: a separate public repository and static pages (the recommendation), under the same organisation; and **who holds the catalog key** (one maintainer's hardware token, or two keys with a threshold), with a second key shipped for rotation
- **Unsigned level 0** from a file: allowed after a warning (the recommendation, so a person can write a theme in minutes) or only with a signature
- **Level 2** (the user wants every level): the order (after phase 3, the recommendation), the **spike on Node's permission model** deciding whether *restricted* is real on all three systems, **unrestricted only with a signature and a typed confirmation** (the recommendation), and whether the official catalog hosts level 2 at all or only lists it with the warning
- **The file name** `.fbplugin` and the word the interface uses (**Extensions**, as the design says, or Plugins)
- **Publisher identity**: the namespace rule by the owner of the repository on GitHub (the recommendation), or by a verified e-mail
- **Third-party catalogs**: not in version 1 (the recommendation), or allowed in developer mode with their own key
- **The API's stability policy** (semver of `api`, a deprecation period of one minor release) before any level 1 extension is accepted
