## Extensions (plugins): a warning at install plus a safe mode (after 0.1.3; priority Later, after the registries it needs)
**Decision of the owner, 2026-10-09 (the trust model):** extensions are **as flexible as possible, with little limitation; at most a warning for the user to validate**. Chosen among three models: **a warning at install plus a safe mode**. In short (the full text and the reasons are in [`docs/EXTENSIONS-DESIGN.md`](../EXTENSIONS-DESIGN.md), section 0, which **replaces** the earlier sandbox model):
- **Full power for the extension** (Node, the network, processes, files) and **no sandbox**. So the former levels 1 (code in a box with no network) and 2 (a process, off by default) are **one**: real code in a **process separate from the main one** (so a hang, a loop or a crash cannot take the application down and the user can always switch it off). **Level 0** (declarative: menu items, commands, themes, key schemes, file type associations) stays.
- **A warning at install**: the publisher, **signed or not**, the **origin** (file, repository URL and commit, or catalog) and what the extension **declares** it will use: informative, not restrictive; the user confirms. **Installing unsigned is allowed** (free side load, with the warning).
- **Three sources**: a local file or folder (side load), **a repository** (`owner/repo` or a Git URL, public or private; planned, phase 7) and the **curated, signed catalog** hosted by the project (opt-in).
- **Safe mode** (`--safe-mode` and a button) starts with no extension; an **activity log** records what each extension did (files written, processes started): transparency, not restriction.
- **The application's API protects** (trash, atomic writes, Local History, authorised roots) whoever uses it; an extension that does things on its own is on its own, and the warning says so. **The README and the guide must say clearly that "nothing leaves the computer" and "writes only inside the authorised roots" are guarantees of the core, not of third-party extensions.**
- **The core keeps the basics** (browse, view PDF, image, media and hex, edit text, diff, ZIP, file operations, trash). **Extensions**: PDF manipulation (rotate, delete and reorder pages, merge, annotate, forms), image editing and EXIF, tar and 7z, playlists, "file intelligence" packs. **The first extension that proves the API: "PDF: rotate, delete and reorder pages"** (or rotate and crop an image).
- **Local History** (the safety net, `docs/todo/files.md`) must exist **before or together with** the extensions that write over originals.
- **Zero entry cost to author** (also the owner's requirement): the **authoring kit** (a guide for agents, a typed API, templates, the `fb-plugin` tool, a reloading development mode) is born **with the API**, documentation first; anyone with an idea can make an extension (phase 3b).

Common to every phase: the **performance rule** at the top of `TODO.md` (a budget before the code, a test that fails when it is exceeded, numbers in the pull request); a change is complete with its tests, `CHANGELOG.md` lines, `TODO.md` boxes and docs (the README and the guides in both languages). Cost: S days, M a week or two, L weeks.

Phase 1: the registries (prerequisite; size M; **blocked by**: nothing; it is the Settings framework, the command registry and the key table, each useful alone)
- [ ] **The settings registry and framework** (see `docs/todo/settings.md`): a registry the Settings page is built from that **accepts contributions**, a file the application owns (`settings.json`), JSON, export and import, validated on every write and read
- [ ] **The command registry** (palette, menus and shortcuts built from typed entries; the built-in features use it too) and the **editable key table** with the **reserved keys** (`Ctrl+S`, `Ctrl+W`, `Delete`…) an extension cannot bind
- [ ] **Open With custom command** and the runner that starts a program **without a shell**, one argument per value (`{file}` is one argument), used later by level 0 entries
- [ ] **Registries for the other contribution points**: themes (colour tokens in `theme/tokens.css` as data), key schemes, languages (file type to language) and locales
- **Budget**: the start of the application does **not** get slower; reading a registry is O(1); the Settings page opens in one frame with 500 entries; a search in it does not block typing. **Closed by**: unit tests of every registry (a duplicate id, a wrong type, an out-of-range value, reset, export and import), the reserved keys refused, the runner tested with arguments that contain quotes, `$`, `&` and a leading `-` (no shell, one argument), an e2e spec that changes a setting, restarts and finds it, and the start-up time measured before and after

Phase 2: the host and level 0 (size L; **blocked by**: phase 1)
- [ ] **The manifest** (`schema: 1`, `plugin.json`) and its **JSON Schema**, with a validator that builds a **new, strict object** from the JSON (size and depth limits, no prototype pollution, strings kept as text); the manifest has `uses` (declared, informative) and no permission grants
- [ ] **The package reader** (`core/extensions/package.ts`, plain TypeScript, no Electron): the same extension works as **a folder** (an unpacked folder or a repository checkout) **and as a packed `.fbplugin`** (a ZIP); limits on size, files, ratio and names (`safeRelative`), no symbolic links, no absolute or `..` names, the **file hashes** checked against the manifest, the optional **ed25519 signature** (the code of `core/validate/signature.ts` and the store of trusted signers `core/signers.ts` are reused), and the trust label (**From the catalog**, **Signed by a publisher you trust**, **Signed, unknown publisher**, **From a repository**, **Unsigned**); a fuzz and bomb corpus in `fixtures/hostile.ts`
- [ ] **Manual install (side load) and remove**: File ▸ **Install Extension from File…**, drop a `.fbplugin` or a folder on the Extensions page; an **atomic** unpack to `userData/extensions/<id>/<version>/` (read-only), a small `installed.json` index (the only thing read at start), a **rollback** to the previous version, **uninstall**; a basic confirmation (the full warning is phase 4)
- [ ] **Level 0 contributions working**: themes (with a preview and a reset), key schemes (reserved keys refused), language packs and file-type to language, snippets, **Open With entries and commands** (a program and arguments, run by the application, confirmed again on the first run), menu entries that call those commands; **developer mode** (an unpacked folder, reloaded on change, a banner while on, off by default)
- [ ] **The Extensions page** in Settings: Installed (enable and disable, version, publisher, trust label, what it contributes, size, **Open its folder**, remove), **Disable All**
- [ ] **Settings of an extension** (`contributes.configuration`, `docs/EXTENSIONS-DESIGN.md` section 3b): declared in the manifest (types `boolean`, `enum`, `number`, `string`, `colour`, `list`, `key`, `folder`, `file`, `action`; **at most 100 per extension, strings 4 KB, lists 1,000 items, no regular-expression patterns**) and **made into entries of the settings registry at install**, listed, searched, validated, stored, reset, exported and imported with **no extension code running**; stored under `extensions.<id>` in `settings.json`, validated on every write and read, `renamedFrom`, uninstall asks to keep or delete; level 0 contributions use an option as **one validated argument**; an option that changes what the extension reaches is never kept silently across an update nor taken from an import
- [ ] **Compiled at install**: contributions go into the registries when the extension is installed, so start-up reads one small index; nothing is activated until its `activation` event
- **Budget**: the start is **not slower** with 50 level 0 extensions installed; the Extensions page with 100 entries opens in one frame; an install of a package of 5 MB does not freeze the interface. **Closed by**: tests of the schema (good, missing field, wrong type, huge, deep, `__proto__`), the package reader against every hostile case (`../`, absolute, symlink, ZIP bomb, a million files), hashes, trust labels, install, update, rollback and uninstall, a theme and a key scheme applied and removed, an Open With command with hostile arguments, and an e2e spec (install from a file, see its theme, restart, disable it, remove it)

Phase 3: the extension process and the application's API (size L; **blocked by**: phase 2; **documentation first**: the contract of the API is written, with its `.d.ts`, before the code, and the code is checked against it)
- [ ] **The runtime**: an Electron `utilityProcess` per extension with code, started on activation and stopped when idle, with **no access to the interface's window, its IPC or `window.fb`**; a message port to the main process; a **restart** button and a notice on a crash or a hang; the host **stops** a process that hangs or grows without limit; a spike (written in the design) on how to start it, hand it a port and kill it on Linux, Windows and macOS
- [ ] **The application's API** (versioned, `api: 1`, a stability and deprecation promise): **files through the guard** (`resolveInside`, no link out of a root; read bytes by range or whole; **write atomically**; delete **to the trash**; a **Local History** copy before overwriting an original), the **selection** (the marked rows), **commands and menu entries**, **notifications and progress with cancellation**, **settings** (`settings.get`, `getAll`, `onChange`, debounced and batched; an extension reads only its own options), storage of its own. Every call is **validated as `unknown`**, batched and throttled like the interface's IPC. **Using it is optional** (the extension may use Node directly; the protections then do not apply)
- [ ] **Extension points, one by one**, each with its tests and its example: commands on the selection or the text (the "Text tools" as the first, built through the same point), **viewers** for a file type, **transformations** ("bytes in, bytes out" for a file or a selection), **status bar items**, **side panels** (labelled with the extension's name and a "from an extension" mark); a point is added only when a built-in feature or a first-party extension has used it
- [ ] **Helper programs**: an extension ships a program per system (hash-pinned in the manifest, run from the installed read-only copy) or uses one on the computer; declared in `uses`
- [ ] **Until phase 4 is in, an extension with code installs only in developer mode** (so no code runs without the warning)
- **Budget**: a call through the API adds under a millisecond locally and under a few milliseconds with a file read of 1 MB; a started extension does **not slow typing** in the editor; an idle extension costs no memory (its process is stopped); the API streams and reads by range, never a whole big file. **Closed by**: every call of the API tested for a path that leaves a root, a `..`, a symlink out, a wrong type; the API's atomic write, trash and Local History copy tested; a hung, a looping and a memory-hungry extension contained and the window alive; the `.d.ts` generated from the code and checked in CI; an e2e spec with a made-up extension with code that is installed, runs a command on the selection and is restarted after a crash

Phase 3b: the authoring kit, "zero entry cost" (size L; **blocked by**: it starts with phase 3 and ends after it; **gates phase 5**; **documentation first**)
**The owner's requirement (2026-10-09):** anyone with an idea in their head and the will can make an extension; the documentation is what other agents use to create them.
- [ ] **The guide for agents**: `PLUGIN-AUTHORING-FOR-AGENTS.md`, one self-contained file in English (the mental model; the manifest; each contribution: a command, a menu item, a file type, a viewer, "bytes in, bytes out"; the API with short examples; do's and don'ts; common mistakes and their fix), plus a Claude Code **skill** (`fb-plugin-author`) and an **`AGENTS.md`** the user drops in any folder; the human guide `docs/EXTENSIONS.md` in English and Brazilian Portuguese from the same sources
- [ ] **The typed API** (`.d.ts`): generated from the code, published with the application and as a package; stale or broken fails the build
- [ ] **Templates and working examples**: a command, a file type, a **PDF transformation**, an **image transformation**, a viewer; each one builds, tests and installs (CI)
- [ ] **The `fb-plugin` tool**: `new` (a skeleton from a sentence), `validate`, `test` (a harness that simulates the application: a fake host API, a virtual file system, a clock), `pack` (the `.fbplugin`), `install --dev`; offline, `--json` output and stable error codes with a one-line fix each
- [ ] **A development mode that reloads automatically** inside the application (from an unpacked folder) and **clear errors that say what to fix** (the field, the rule, an example)
- [ ] **JSON Schemas** (`docs/schema/*.json`) for the manifest, the repository manifest, the catalog index and the blocklist; the guide's code blocks are run by a test (a broken example fails the build)
- **Budget**: `fb-plugin validate` under a second; `test` of a template under 10 seconds; reload in the development mode under a second. **Closed by**: the **acceptance test of the kit**: an agent that reads **only** the guide and the typed API writes, validates, tests and installs a new extension **at the first attempt, without help**, from a **one-sentence idea**; run on at least five ideas of different kinds with a fresh agent each time, the results recorded in the pull request. **The phase closes only when this passes.** Also: every template built from its template by CI and installed in an e2e spec, the schemas accepting every example and rejecting the hostile ones, and `fb-plugin validate --json` giving the same codes the install screen shows

Phase 4: the install warning, the safe mode and the activity log (size M; **blocked by**: phase 3)
- [ ] **The install warning**: name and version, **publisher**, **signed or not** and by whom (the key's fingerprint), the **origin** (file path, repository URL and commit or tag, or catalog), what it contributes, what it **declares** it will use (`uses`), size, and a plain line that code **runs with full power and is not confined by the application**; the user confirms; **unsigned is allowed**; nothing installs from a drop, a link or an import without it; an update that **grew the declared uses** asks again with the difference
- [ ] **Safe mode**: `--safe-mode` and File ▸ **Restart Without Extensions**, offered after a crash at start-up; no extension code and no level 0 data is applied
- [ ] **The activity log**: per extension, bounded: the files written through the API, the processes the host started, with the time; shown in Extensions ▸ <name> ▸ Activity, with a line that it records what the API and the host saw and cannot see what an extension does on its own
- [ ] **The words in the README and the guides**: "nothing leaves the computer" and "writes only inside the authorised roots" hold for the core, not for third-party extensions (README and user guide in both languages, the install screen)
- [ ] The restriction that an extension with code installs only in developer mode (phase 3) is lifted here
- **Budget**: the warning opens in under 100 ms from a package already read; the log appends in batches, never one write per event, and stays under a size limit; safe mode starts as fast as a normal start. **Closed by**: tests that the warning shows every field for each source (a file, a folder, a repository, a catalog entry) and never installs without a click; a drop, a link and an import do not install by themselves; the growth of `uses` is shown; safe mode runs no extension (an e2e spec with a crashing extension: restart without extensions); the log records an API write and a started process and is bounded; the README claim is checked by a docs test

Phase 5: the first real extension, "PDF: rotate, delete and reorder pages" (size M to L; **blocked by**: phases 3, 3b and 4, and **Local History** (`docs/todo/files.md`, "Safety net"), which must exist before it writes over originals)
- [ ] The extension in its own folder (`extensions/pdf-pages/`, signed by the project, **Built in** or **Official**, decided here), using only the API: the PDF reader stays in the core (pdf.js) and the extension adds a page strip, rotate, delete and reorder, and writes the result through the API's atomic write after a Local History copy; a fallback choice is "rotate and crop an image"
- [ ] The API points it needs, **and only those**, added to the API with their examples in the guide (the API grows from use); the extension is also the guide's worked example
- [ ] The messages and the guide in both languages; the `[ext]` tag in `docs/todo/pdf.md` and `docs/todo/extension-first.md`
- **Budget**: a PDF of 1,000 pages opens its page strip with thumbnails drawn lazily (only the visible ones), a rotate or delete of one page of a 100 MB PDF finishes in under 3 seconds without freezing the interface, memory stays bounded (pages read by range). **Closed by**: unit tests of the page operations on synthetic PDFs from `fixtures/`; the original is recoverable from Local History after each operation; the original is untouched if the write fails; an e2e spec (open a PDF, rotate, delete and reorder pages, save, undo through Local History); the extension is installed from its `.fbplugin` in the spec

Phase 6: the curated and signed catalog (size M to L; **blocked by**: phases 4 and 5)
- [ ] **The catalog client** (opt-in, off by default, explained in plain words in Settings ▸ Privacy ▸ Extensions: one HTTPS read of a small index, no identifier, the host sees the IP address): fetches `index.json`, its signature and `revoked.json` **only when the Browse page opens or Check for Updates is pressed** (never at start, never in the background); `ETag` caching; the **catalog's public key is in the application** (and a second for rotation); an index is accepted only if its **signature verifies**, its **`sequence` is not lower** than the last seen and it is **not stale**; a **download only on a click**, checked against the entry's **pinned SHA-256**, the package's own signature and file hashes, then the install warning
- [ ] **Browse**: the list from the signed index (name, summary, publisher, level, categories, declared uses in a line, size, the **From the catalog** mark, an icon loaded lazily after the click), a search and category filter on the index already in memory; **Install**; **Updates** offered, never applied, with the difference in `uses`
- [ ] **Revocation**: the signed blocklist disables an installed extension or a publisher key **at once** and **stops its process**, with a notice that says why; without the catalog turned on the application cannot know, and the page says so
- [ ] **Air gap and mirrors**: **Browse a catalog from a folder**; a mirror is only a cache and still needs the catalog key's signature; another catalog key is a developer-mode setting
- [ ] **The repository side** (`folder-browser-extensions`, public, static): the layout of `catalog/v1/`, a pull request flow for authors, **CI** that validates the schema, sizes, hashes, that a level 0 package has no code, that the declared `uses` match the description, the **publisher namespace rule** (against impersonation and typosquatting), the hostile-package tests; a **human review of the source** for every extension with code and for any growth of `uses` (the curators check the declaration against the code); **offline signing** of each publication with the key on a hardware token; `docs/EXTENSIONS-POLICY.md` (what may be published, how to report a malicious one, **takedown and revocation** with a time target, key rotation, the API stability promise)
- **Budget**: the index is small and gzipped, sharded by id prefix past a limit, parsed off the interface's thread, held in memory only while the page is open; no request per keystroke. **Closed by**: a fake catalog server for every case (a bad signature, an older `sequence`, a stale index, a hash that does not match, a package signed by another key, a revoked extension and key, a mirror with the wrong key, a download cut off, a huge index); the page's states (off, offline, loading, the list, an error in plain words); the `uses`-difference screen; an e2e spec against a local fake catalog (browse, install, update offered, revoke)

Phase 6b: the distribution channel of the catalog (size M; an infrastructure and operations job more than code; with phase 6)
The catalog of phase 6 is **the channel**: this phase makes it a real, reachable and operated service. It stays **static, with no accounts and no server code**; **the trust is in the signatures, not in the host**.
- [ ] **The catalog repository** (`folder-browser-extensions`, public, with its own `README`, `CONTRIBUTING`, `SECURITY` and issue templates): the layout of `catalog/v1/` (`index.json`, `index.json.sig`, `revoked.json`, `revoked.json.sig`, `icons/`), a pull request template for a new extension and an update, the CI that validates it, a protected `main`
- [ ] **Hosting and mirrors**: static pages (GitHub Pages first) with the **same files mirrored** to a second host, listed in the application as the default and a fallback; the packages are release assets of each author's repository (or of the catalog's for a first-party extension), each pinned by its SHA-256
- [ ] **The public page of the catalog** on the site (`docs/todo/positioning.md`, "A site"): a list generated from `index.json` with a permalink per extension, a **Report** link, and an **Install** button that opens the application (a `folder-browser://extension/<id>` link that shows the install warning: it **never installs by itself**)
- [ ] **Publishing made easy**: `fb-plugin publish` prepares the package, signs it, checks it against the conformance list and opens the pull request on the author's behalf
- [ ] **Operations**: the offline signing ceremony for each publication, key rotation and leaked-key procedures rehearsed, an abuse report channel with a **time target for takedown and revocation**, a **transparency log** (every publication, removal and revocation is a commit) and a status page
- [ ] **Policy and moderation**: `docs/EXTENSIONS-POLICY.md`, a review checklist for code, a code of conduct
- **Later options, not now**: publisher verification beyond the namespace rule; ratings or comments (not planned); paid extensions (not planned); a private catalog for a company (the mirror path covers it)
- **Budget and tests**: the client costs one small request on demand; the site is static and cached; the CI rules tested with hostile submissions (a typosquat, a level 0 package with code, a growth of `uses`, an id owned by someone else, a bad signature, a duplicate version); a dry run of the whole publication on a staging copy and an install from it in an e2e spec before every real one

Phase 7: install from a repository (size M to L; **blocked by**: phase 6 (the trust labels, the install warning and the fetch of a signed index are reused); the design reserves it from the start, `docs/EXTENSIONS-DESIGN.md` section 5b)
**The owner's addition (2026-10-09):** "the possibility of installing plugins from a repository in the future; our specification must provide for it."
- [ ] **The source**: `owner/repo` of GitHub (public or private) or the URL of a Git repository, plus an optional ref (tag or branch); the folder in the repository is the extension (`plugin.json` at the root or at a path), the **same layout as the packed `.fbplugin`**
- [ ] **The repository manifest ("marketplace")**: `fb-marketplace.json` in a repository lists several extensions (`name`, `owner`, `extensions[]` with `id`, `name`, `description`, `version`, and a `source` that is a path relative to the repository or another repository with a `ref` and `commit`), in the style of Claude Code's `marketplace.json`; the user adds a repository as a source and sees the list
- [ ] **Pinned versions and the lock file**: every install is at a **commit or tag resolved to a full commit hash**, never "the latest of the branch" without the user knowing; `extensions.lock.json` records the source, the ref asked for, the commit installed, the version and a hash of the installed tree, so an install is **reproducible** (export and import of the lock; an import is an install, with the warning for each entry); a tag that moved is reported
- [ ] **Fetching without Git installed**: the host's archive at the commit (for GitHub the `zipball`) read with the ZIP reader, with git over HTTPS as a fallback; **private repositories** through the user's existing credentials (`gh` or the Git credential helper) or the system's key store (`safeStorage`), never a token in `settings.json`, a token sent only to the repository's host
- [ ] **The warning shows the origin** (repository URL, commit or tag, publisher) as well as the signature and what it declares (phase 4's screen, with the origin line)
- [ ] **Updates**: **never automatic by default**; an opt-in check for news (on demand, or at most daily if the user turns it on) compares each source with the lock; the update screen **shows what changed between the two commits** (changed files, the manifest's difference in `version`, `uses` and `contributes`, a link to the host's compare page) and the user confirms; a growth of `uses` is highlighted
- [ ] **Uninstall and revert**: the previous version is kept (one back), **Revert** returns to it in one click and updates the lock; uninstall removes the folder, the lock entry and (the user chooses) the data and settings
- **Budget**: listing a repository's manifest reads one small file; an install downloads one archive (not the history) and reports progress and can be cancelled; the check for news is opt-in and costs one request per source; nothing runs at start. **Closed by**: a fake Git host for every case (a tag that moves, a branch that changes between the list and the install, a commit that was force-pushed away, a private repository with and without credentials, an archive cut off, a huge archive, a hostile path in the archive, a `source` that points at another repository, a lock imported on another computer reproducing the same bytes); the origin shown on every screen; no automatic update; revert restoring the previous version; an e2e spec against a local fake host (add a repository, install, see the update diff, update, revert)

Performance and security (a requirement of every phase, per the rule at the top)
- [ ] The start of the application does not wait for extensions (a small index, activation on demand, contributions compiled at install); the catalog and repository fetches are on demand, small and cancellable; the **activity log and the Extensions page** are the user's way to see what an extension does; the **security scan** (`/claude-security`, only when the user asks, see "Light use" in `CLAUDE.md`) of the extension host, the API and the package reader before each phase is released: note that, without a sandbox, the API's guard and the install warning are where the care goes

Decisions to make before this is started (the open questions are numbered in `docs/EXTENSIONS-DESIGN.md`, section 11)
- **The package and the signature**: `.fbplugin` as a ZIP with `plugin.json` and an optional ed25519 `SIGNATURE`, the same layout as a folder in a repository; who signs what
- **Where the code runs and how it talks to the application**: a `utilityProcess` per extension and a `MessagePort` (the proposal), a helper program per system, and the **minimum API a PDF extension needs** (read bytes by range, atomic write with a Local History copy, the selection, a command and menu entry, progress and cancellation, a notification, settings)
- **Safe mode and the activity log**: what is recorded when an extension uses Node directly (the page says it cannot see); whether safe mode skips level 0 data too
- **The catalog**: where it is hosted and mirrored, **who holds the catalog key** and the second key for rotation, the takedown time target, whether first-party extensions live in the catalog's repository or in this one
- **Installing from a repository**: authentication to a private repository (`gh` or Git credentials, the key store or a pasted token), fetching without Git installed and for hosts other than GitHub, how the commit is pinned and verified (commit hash plus tree hash; a force-push that removes the commit), the exact format of `fb-marketplace.json` and whether it reuses Claude Code's `marketplace.json` field for field
- **The authoring kit**: how many ideas and which agents make the acceptance test (the proposal: five ideas of different kinds, a fresh agent each, all working first time); where the skill and `AGENTS.md` live; whether `fb-plugin` and the `.d.ts` are npm packages; how `new` makes a skeleton from a sentence
- **The word** the interface uses (**Extensions**, as the design says, or Plugins)
- **The API's stability policy** (semver of `api`, a deprecation period of one minor release) before any extension with code is accepted into the catalog
- **Which first-party extensions are Built in and which Official**, and whether a built-in extension may be uninstalled or only disabled
