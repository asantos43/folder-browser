## Plugins: a warning at install plus a safe mode (after 0.1.3; priority Later, after the registries it needs)
**The word (decided 2026-10-09): "Plugins"** in the interface and in the plan (the Plugins menu, "Install Plugin…", the guide "Create a plugin"); this file and `docs/EXTENSIONS-DESIGN.md` keep their names so that no link breaks. **Other decisions of the owner of 2026-10-09** (the reasons and the details are in `docs/EXTENSIONS-DESIGN.md`, section 11): the package is a `.fbplugin` ZIP with `plugin.json`, the code and an **optional ed25519 signature** (unsigned installs, with the warning; the same layout as a folder in a repository); the code runs in **one process per plugin** (`utilityProcess`, `MessagePort`); the repository manifest is **compatible with Claude Code's `marketplace.json`** (replaces `fb-marketplace.json`); **one provider version of an exported API at a time**; updating a provider **keeps the plugins that depend on it off until they are updated**, with a message that says which; installing a plugin with dependencies is **automatic after the warning of the whole tree**; the acceptance test of the authoring kit is a **capability matrix** (phase 3b).
**Decision of the owner, 2026-10-09 (the trust model):** plugins are **as flexible as possible, with little limitation; at most a warning for the user to validate**. Chosen among three models: **a warning at install plus a safe mode**. In short (the full text and the reasons are in [`docs/EXTENSIONS-DESIGN.md`](../EXTENSIONS-DESIGN.md), section 0, which **replaces** the earlier sandbox model):
- **Full power for the plugin** (Node, the network, processes, files) and **no sandbox**. So the former levels 1 (code in a box with no network) and 2 (a process, off by default) are **one**: real code in a **process separate from the main one** (so a hang, a loop or a crash cannot take the application down and the user can always switch it off). **Level 0** (declarative: menu items, commands, themes, key schemes, file type associations) stays.
- **A warning at install**: the publisher, **signed or not**, the **origin** (file, repository URL and commit, or catalog) and what the plugin **declares** it will use: informative, not restrictive; the user confirms. **Installing unsigned is allowed** (free side load, with the warning).
- **Three sources**: a local file or folder (side load), **a repository** (`owner/repo` or a Git URL, public or private; planned, phase 7) and the **curated, signed catalog** hosted by the project (opt-in).
- **Safe mode** (`--safe-mode` and a button) starts with no plugin; an **activity log** records what each plugin did (files written, processes started): transparency, not restriction.
- **The application's API protects** (trash, atomic writes, Local History, authorised roots) whoever uses it; a plugin that does things on its own is on its own, and the warning says so. **The README and the guide must say clearly that "nothing leaves the computer" and "writes only inside the authorised roots" are guarantees of the core, not of third-party plugins.**
- **The core keeps the basics** (browse, view PDF, image, media and hex, edit text, diff, ZIP, file operations, trash). **Plugins**: PDF manipulation (rotate, delete and reorder pages, merge, annotate, forms), image editing and EXIF, tar and 7z, playlists, "file intelligence" packs. **The first plugin that proves the API: "PDF: rotate, delete and reorder pages"** (or rotate and crop an image).
- **Local History** (the safety net, `docs/todo/files.md`) must exist **before or together with** the plugins that write over originals.
- **Plugins on plugins (the onion)**: a plugin can export an API (a versioned `.d.ts` contract) and other plugins depend on it, in layers without cycles, calls mediated by the application, big data by reference (phase 5b); intercepting another's calls is planned, not built.
- **Zero entry cost to author** (also the owner's requirement): the **authoring kit** (a guide for agents, a typed API, templates, the `fb-plugin` tool, a reloading development mode) is born **with the API**, documentation first; anyone with an idea can make a plugin (phase 3b).

Common to every phase: the **performance rule** at the top of `TODO.md` (a budget before the code, a test that fails when it is exceeded, numbers in the pull request); a change is complete with its tests, `CHANGELOG.md` lines, `TODO.md` boxes and docs (the README and the guides in both languages). Cost: S days, M a week or two, L weeks.

**What exists today** (so that nothing is built twice): *commands* are the `Commands` interface and `MENUS` in `src/workbench/commands.ts` (labels and shortcuts typed by hand), a `run` chain of `if`s in `Workbench.tsx`, a palette that walks `MENUS` (`QuickOpen.tsx`), the native macOS menu with its own list (`electron/menu.ts`), and context menus by kind of row (`treeMenu.ts` and others); *keys* are `commandFor` in `core/shortcuts.ts` (read by `electron/shortcuts.ts` and by the window's `keydown`; a snapshot's frame never lets the window see a key, which is why the main process reads the same table), plus local keys in widgets (CodeMirror, `Alt+Z`, `F7`, `F2`, `Delete`) and the shortcut strings written by hand in menus and `electron/menu.ts`; *settings* are 15 `createSetting` values plus the theme and the language in the window's `localStorage` (`src/state/setting.ts`, `src/lib/storage.ts`), a hand-written page (`SettingsView.tsx`), and the main process's own small files (`session.json`, `recent-*.json`, `favorites.json`, `trusted-signers.json`).
**The design**: ids of the core have no colon and ids of a plugin are `<plugin id>:<name>` (commands, settings); a command has a title (an existing message key), a category, a `when` and default keys, and **menu, palette and shortcut are views of the same registry**; `when` is a tiny condition (`a && !b`, `x == 'y'`), compiled once, no `eval`; keys are chords (`Mod+S`, `Ctrl+Tab`; `Mod` is Ctrl or Command) in **one table read by both processes**, priority user > plugin > core, a plugin cannot take a reserved chord, conflicts are listed; the user's keys are `keybindings.json` (a list as in VS Code, `-command` removes a default); settings are a registry (boolean, choice, number, string, colour, list; `category.name` ids) with a `settings.json` **owned by the main process** (atomic, validated on read and write, unknown keys kept, a plugin's options nested in `plugins.<id>`), changes batched, the page generated from the registry; layout state (side bar width) stays in `localStorage`.

Phase 3: the plugin process and the application's API (size L; **blocked by**: phase 2; **documentation first**: the contract of the API is written, with its `.d.ts`, before the code, and the code is checked against it)
- [ ] **The runtime**: an Electron `utilityProcess` per plugin with code, started on activation and stopped when idle, with **no access to the interface's window, its IPC or `window.fb`**; a message port to the main process; a **restart** button and a notice on a crash or a hang; the host **stops** a process that hangs or grows without limit; a spike (written in the design) on how to start it, hand it a port and kill it on Linux, Windows and macOS
- [ ] **The application's API** (versioned, `api: 1`, a stability and deprecation promise): **files through the guard** (`resolveInside`, no link out of a root; read bytes by range or whole; **write atomically**; delete **to the trash**; a **Local History** copy before overwriting an original), the **selection** (the marked rows), **commands and menu entries**, **notifications and progress with cancellation**, **settings** (`settings.get`, `getAll`, `onChange`, debounced and batched; a plugin reads only its own options), storage of its own. Every call is **validated as `unknown`**, batched and throttled like the interface's IPC. **Using it is optional** (the plugin may use Node directly; the protections then do not apply)
- [ ] **Plugin points, one by one**, each with its tests and its example: commands on the selection or the text (the "Text tools" as the first, built through the same point), **viewers** for a file type, **transformations** ("bytes in, bytes out" for a file or a selection), **status bar items**, **side panels** (labelled with the plugin's name and a "from a plugin" mark); a point is added only when a built-in feature or a first-party plugin has used it
- [ ] **Helper programs**: a plugin ships a program per system (hash-pinned in the manifest, run from the installed read-only copy) or uses one on the computer; declared in `uses`
- [ ] **Until phase 4 is in, a plugin with code installs only in developer mode** (so no code runs without the warning)
- **Budget**: a call through the API adds under a millisecond locally and under a few milliseconds with a file read of 1 MB; a started plugin does **not slow typing** in the editor; an idle plugin costs no memory (its process is stopped); the API streams and reads by range, never a whole big file. **Closed by**: every call of the API tested for a path that leaves a root, a `..`, a symlink out, a wrong type; the API's atomic write, trash and Local History copy tested; a hung, a looping and a memory-hungry plugin contained and the window alive; the `.d.ts` generated from the code and checked in CI; an e2e spec with a made-up plugin with code that is installed, runs a command on the selection and is restarted after a crash

Also: every template built from its template by CI and installed in an e2e spec, the schemas accepting every example and rejecting the hostile ones, and `fb-plugin validate --json` giving the same codes the install screen shows

- [ ] The API points it needs, **and only those**, added to the API with their examples in the guide (the API grows from use); the plugin is also the guide's worked example
- [ ] The messages and the guide in both languages; the `[ext]` tag in `docs/todo/pdf.md` and `docs/todo/extension-first.md`
- **Budget**: a PDF of 1,000 pages opens its page strip with thumbnails drawn lazily (only the visible ones), a rotate or delete of one page of a 100 MB PDF finishes in under 3 seconds without freezing the interface, memory stays bounded (pages read by range). **Closed by**: unit tests of the page operations on synthetic PDFs from `fixtures/`; the original is recoverable from Local History after each operation; the original is untouched if the write fails; an e2e spec (open a PDF, rotate, delete and reorder pages, save, undo through Local History); the plugin is installed from its `.fbplugin` in the spec

Phase 5b: plugins on plugins, the onion (size L; **blocked by**: phase 5 (the first real plugin, `pdf-pages`, is the first exporter), phase 3b (the kit must cover it) and, for dependencies from a repository, phase 7 (build the graph so a `source` is already allowed in the manifest, and add the repository fetch when phase 7 lands); design: `docs/EXTENSIONS-DESIGN.md` section 9b)
**The owner's concept (2026-10-09):** plugins on top of plugins, like an onion: a plugin exports an API of its own that other plugins consume. Intercepting another's calls is **planned, not built now**.
- [ ] **The manifest**: `exports` (`api` name, semver `version`, `types` the `.d.ts` of the contract) and `dependsOn` (`api`, semver `range`, `source`: the catalog, a file or a **repository**, linked to "install from a repository"); the schema and the JSON Schema (`docs/schema/*.json`) updated; `intercepts` is **reserved and rejected by the validator** for now
- [ ] **The graph**: loaded in the order of dependencies (an inner layer on demand, when an outer layer activates); **a cycle is an install error that names it**; a duplicated exported name is an error naming both; the version range checked before activation
- [ ] **The mediated call**: a consumer's call goes through the host to the provider's process; **async, typed by the contract, validated as `unknown`**; **large data as references** (a file the guard knows, a handle or a stream), never bytes; an inline limit (a few hundred KB) refused with a message that says to pass a reference; cancellation and progress carried along; the call logged in the activity log (consumer, provider, method, size, time)
- [ ] **Clear failure**: a missing, disabled or incompatible dependency turns off the dependent plugin with a message that says **what to install** (API, range, source); the application **warns and lists the dependents before** removing, disabling or updating a provider
- [ ] **The install warning covers the whole tree** (every origin, version, publisher, signature and declared use, transitive) and the **lock file records the resolved tree with commits**; an update shows who depends on the layer and whether the contract's version changed
- [ ] **Versions**: a breaking change of a contract is a major version (checked by `fb-plugin validate` against the previously published `.d.ts`); **one provider version at a time** (decided 2026-10-09): if the ranges of two consumers do not meet, the application says which plugin must be updated; versions side by side are a possible later evolution. **Updating a provider** keeps the plugins that depend on it **off until they are updated**, with a message that lists them. **Installing a plugin with dependencies is automatic after the warning of the whole tree** (one "Confirm" installs all)
- [ ] **The kit covers it**: `fb-plugin new --depends-on <api>`, `validate` for the contracts, ranges and graph, the test harness with a **simulated dependency** (a fake provider built from the `.d.ts`), a chapter and a worked example in the guide; the acceptance test of the kit gets one idea that needs a dependency
- [ ] **The guide example**: `pdf-pages` exports the page operations; `pdf-merge` and `pdf-annotate` consume them
- [ ] **Prepared, not built**: the contract format stays wrappable (every exported method is an async function over plain data; provider name and version travel with each call) for a later "intercept" in the style of the `next(e)` of Claude Code's mods; its risks (an outer layer breaking the inner ones, order between wrappers, a delay on every call) are written in the design
- **Budget**: a call with small values adds under a millisecond locally beyond the process hop; a call about a 500-page PDF (about 50 MB) copies **no bytes** between processes (the test measures bytes crossing); building the graph of 50 plugins takes under 50 ms and happens at install, not at start; an unused layer stays stopped. **Closed by**: tests of a cycle, a duplicated name, a missing, a disabled and an incompatible dependency (each with the message that says what to install); removing a provider that has dependents warns; the tree warning for a three-layer install from a fake repository; the lock reproducing the tree; a breaking contract change flagged by `validate`; the mediated call validated (a wrong type, a huge inline value refused, cancellation); an e2e spec with `pdf-pages` and `pdf-merge` (install `pdf-merge`, see `pdf-pages` in the warning, merge two PDFs through the call)

Phase 6: the curated and signed catalog (size M to L; **blocked by**: phases 4 and 5)
- [ ] **The catalog client** (opt-in, off by default, explained in plain words in Settings ▸ Privacy ▸ Plugins: one HTTPS read of a small index, no identifier, the host sees the IP address): fetches `index.json`, its signature and `revoked.json` **only when the Browse page opens or Check for Updates is pressed** (never at start, never in the background); `ETag` caching; the **catalog's public key is in the application** (and a second for rotation); an index is accepted only if its **signature verifies**, its **`sequence` is not lower** than the last seen and it is **not stale**; a **download only on a click**, checked against the entry's **pinned SHA-256**, the package's own signature and file hashes, then the install warning
- [ ] **Browse**: the list from the signed index (name, summary, publisher, level, categories, declared uses in a line, size, the **From the catalog** mark, an icon loaded lazily after the click), a search and category filter on the index already in memory; **Install**; **Updates** offered, never applied, with the difference in `uses`
- [ ] **Revocation**: the signed blocklist disables an installed plugin or a publisher key **at once** and **stops its process**, with a notice that says why; without the catalog turned on the application cannot know, and the page says so
- [ ] **Air gap and mirrors**: **Browse a catalog from a folder**; a mirror is only a cache and still needs the catalog key's signature; another catalog key is a developer-mode setting
- [ ] **The repository side** (`folder-browser-plugins`, public, static): the layout of `catalog/v1/`, a pull request flow for authors, **CI** that validates the schema, sizes, hashes, that a level 0 package has no code, that the declared `uses` match the description, the **publisher namespace rule** (against impersonation and typosquatting), the hostile-package tests; a **human review of the source** for every plugin with code and for any growth of `uses` (the curators check the declaration against the code); **offline signing** of each publication with the key on a hardware token; `docs/PLUGINS-POLICY.md` (what may be published, how to report a malicious one, **takedown and revocation** with a time target, key rotation, the API stability promise)
- **Budget**: the index is small and gzipped, sharded by id prefix past a limit, parsed off the interface's thread, held in memory only while the page is open; no request per keystroke. **Closed by**: a fake catalog server for every case (a bad signature, an older `sequence`, a stale index, a hash that does not match, a package signed by another key, a revoked plugin and key, a mirror with the wrong key, a download cut off, a huge index); the page's states (off, offline, loading, the list, an error in plain words); the `uses`-difference screen; an e2e spec against a local fake catalog (browse, install, update offered, revoke)

Phase 6b: the distribution channel of the catalog (size M; an infrastructure and operations job more than code; with phase 6)
The catalog of phase 6 is **the channel**: this phase makes it a real, reachable and operated service. It stays **static, with no accounts and no server code**; **the trust is in the signatures, not in the host**.
- [ ] **The catalog repository** (`folder-browser-plugins`, public, with its own `README`, `CONTRIBUTING`, `SECURITY` and issue templates): the layout of `catalog/v1/` (`index.json`, `index.json.sig`, `revoked.json`, `revoked.json.sig`, `icons/`), a pull request template for a new plugin and an update, the CI that validates it, a protected `main`
- [ ] **Hosting and mirrors**: static pages (GitHub Pages first) with the **same files mirrored** to a second host, listed in the application as the default and a fallback; the packages are release assets of each author's repository (or of the catalog's for a first-party plugin), each pinned by its SHA-256
- [ ] **The public page of the catalog** on the site (`docs/todo/positioning.md`, "A site"): a list generated from `index.json` with a permalink per plugin, a **Report** link, and an **Install** button that opens the application (a `folder-browser://plugin/<id>` link that shows the install warning: it **never installs by itself**)
- [ ] **Publishing made easy**: `fb-plugin publish` prepares the package, signs it, checks it against the conformance list and opens the pull request on the author's behalf
- [ ] **Operations**: the offline signing ceremony for each publication, key rotation and leaked-key procedures rehearsed, an abuse report channel with a **time target for takedown and revocation**, a **transparency log** (every publication, removal and revocation is a commit) and a status page
- [ ] **Policy and moderation**: `docs/PLUGINS-POLICY.md`, a review checklist for code, a code of conduct
- **Later options, not now**: publisher verification beyond the namespace rule; ratings or comments (not planned); paid plugins (not planned); a private catalog for a company (the mirror path covers it)
- **Budget and tests**: the client costs one small request on demand; the site is static and cached; the CI rules tested with hostile submissions (a typosquat, a level 0 package with code, a growth of `uses`, an id owned by someone else, a bad signature, a duplicate version); a dry run of the whole publication on a staging copy and an install from it in an e2e spec before every real one

Phase 7: install from a repository (size M to L; **blocked by**: phase 6 (the trust labels, the install warning and the fetch of a signed index are reused); the design reserves it from the start, `docs/EXTENSIONS-DESIGN.md` section 5b)
**The owner's addition (2026-10-09):** "the possibility of installing plugins from a repository in the future; our specification must provide for it."
- [ ] **The source**: `owner/repo` of GitHub (public or private) or the URL of a Git repository, plus an optional ref (tag or branch); the folder in the repository is the plugin (`plugin.json` at the root or at a path), the **same layout as the packed `.fbplugin`**
- [ ] **The repository manifest ("marketplace")**, decided 2026-10-09: **compatible with Claude Code's `marketplace.json`** (one repository can serve both), replacing the proposed `fb-marketplace.json`. The file is `.fb-plugin/marketplace.json`; `.claude-plugin/marketplace.json` is accepted too (the first wins if both exist). It lists several plugins (`name`, `owner`, `plugins[]` with `name`, `description`, `version`, and a `source` that is a path relative to the repository or another repository with a `ref` and `commit`). Folder Browser's own fields (the signature, `exports`, `dependsOn`) are an **optional `fb` object** in each entry, so a plain Claude Code marketplace works here and ours does not break Claude Code (to check when built: that Claude Code accepts the extra key; if not, those fields live only in `plugin.json`); the user adds a repository as a source and sees the list
- [ ] **Pinned versions and the lock file**: every install is at a **commit or tag resolved to a full commit hash**, never "the latest of the branch" without the user knowing; `plugins.lock.json` records the source, the ref asked for, the commit installed, the version and a hash of the installed tree, so an install is **reproducible** (export and import of the lock; an import is an install, with the warning for each entry); a tag that moved is reported
- [ ] **Fetching without Git installed**: the host's archive at the commit (for GitHub the `zipball`) read with the ZIP reader, with git over HTTPS as a fallback; **private repositories** through the user's existing credentials (`gh` or the Git credential helper) or the system's key store (`safeStorage`), never a token in `settings.json`, a token sent only to the repository's host
- [ ] **The warning shows the origin** (repository URL, commit or tag, publisher) as well as the signature and what it declares (phase 4's screen, with the origin line)
- [ ] **Updates**: **never automatic by default**; an opt-in check for news (on demand, or at most daily if the user turns it on) compares each source with the lock; the update screen **shows what changed between the two commits** (changed files, the manifest's difference in `version`, `uses` and `contributes`, a link to the host's compare page) and the user confirms; a growth of `uses` is highlighted
- [ ] **Uninstall and revert**: the previous version is kept (one back), **Revert** returns to it in one click and updates the lock; uninstall removes the folder, the lock entry and (the user chooses) the data and settings
- **Budget**: listing a repository's manifest reads one small file; an install downloads one archive (not the history) and reports progress and can be cancelled; the check for news is opt-in and costs one request per source; nothing runs at start. **Closed by**: a fake Git host for every case (a tag that moves, a branch that changes between the list and the install, a commit that was force-pushed away, a private repository with and without credentials, an archive cut off, a huge archive, a hostile path in the archive, a `source` that points at another repository, a lock imported on another computer reproducing the same bytes); the origin shown on every screen; no automatic update; revert restoring the previous version; an e2e spec against a local fake host (add a repository, install, see the update diff, update, revert)

Performance and security (a requirement of every phase, per the rule at the top)
- [ ] The start of the application does not wait for plugins (a small index, activation on demand, contributions compiled at install); the catalog and repository fetches are on demand, small and cancellable; the **activity log and the Plugins page** are the user's way to see what a plugin does; the **security scan** (`/claude-security`, only when the user asks, see "Light use" in `CLAUDE.md`) of the plugin host, the API and the package reader before each phase is released: note that, without a sandbox, the API's guard and the install warning are where the care goes

Decided by the owner on 2026-10-09 (the reasons are in `docs/EXTENSIONS-DESIGN.md`, section 11)
- [x] **The package and the signature**: `.fbplugin` is a ZIP with `plugin.json`, the code and an **optional ed25519 signature**; an unsigned plugin can be installed (the warning shows it); the same layout works as a folder in a repository
- [x] **Where the code runs**: **one process per plugin**, a `utilityProcess` with a `MessagePort`
- [x] **The repository manifest**: **compatible with Claude Code's `marketplace.json`**, at `.fb-plugin/marketplace.json` (also `.claude-plugin/marketplace.json`), with Folder Browser's own fields as an optional `fb` object (signature, `exports`, `dependsOn`)
- [x] **The word**: **Plugins** in the interface (the Plugins menu, "Install Plugin…", the guide "Create a plugin"); the file names `docs/EXTENSIONS-DESIGN.md` and `docs/todo/extensions.md` stay
- [x] **Versions of an exported API**: **one provider version at a time**; side by side is a possible later evolution
- [x] **Updating a plugin from the inside**: the plugins that depend on it **stay off until they are updated**, with a message that says which
- [x] **Installing a plugin that depends on others**: **automatic after the warning of the whole tree**, one "Confirm"
- [x] **The acceptance test of the authoring kit**: the **capability matrix** (every contribution and every API capability is a row with an idea of one sentence; the phase closes when all rows pass; the matrix grows with the API)
