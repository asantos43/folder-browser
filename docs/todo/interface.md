- [ ] **A choice of layout for the two editor groups: side by side or stacked** (priority Next, size S to M): today two groups are always **columns** (one beside the other). Add the **rows** layout (one **above** the other), chosen with **two icons** like the ones of the user's picture, a **segmented control** of two buttons: the first (two columns) for *side by side*, the second (two rows) for *stacked*, the active one drawn filled. It is useful for **long lines** and for **narrow windows** (it also answers the open item about the toolbars that overlap in two narrow groups), and for comparing two files line by line from top to bottom.
  - **Where**: at the right end of the editor area's tab strip, **shown while two groups are open**; the same two choices in the tab's menu (**Split Right** and a new **Split Down**, and **Move to the Other Group**), in the palette and View menu (**Toggle Editor Layout**, a key such as VS Code's `Shift+Alt+0`), and in Settings (the layout a new split starts with).
  - **State**: the layout is part of the workspace (`Workspace.layout: 'columns' | 'rows'`), **kept in the session**, with the **sizes of the two groups** remembered for each; one group only: nothing shown; closing the second group resets nothing.
  - **Behaviour**: the **drop zones** of a dragged tab (`dnd.ts`, `DropLayer`) follow the layout (the left and right halves, or the **top and bottom** halves, and the centre for comparing); the tab menu's words change (**Move Up/Down** for rows); keyboard focus moves between groups by the same keys; the **diff tab's own layout** (side by side or inline, `diffLayout`) stays separate and is not changed by this.
  - **The risk to design for**: changing the orientation **must not remount the groups** (an editor would lose its scroll and state, a **snapshot's frame would reload**: an `<iframe>` moved in the DOM reloads, see `docs/DESIGN-RULES.md`, gotchas), so the container is the same element with another direction, the groups keep their keys, and a test proves that a frame and an editor survive the switch.
  - **Accessibility**: the control is a **radio group** (`role="radiogroup"`, two `radio`s with `aria-checked` and the labels *Side by Side Layout* and *Stacked Layout*), reachable by keyboard, with tooltips; the icons are drawn with the theme's tokens (the filled one is the active), in light and dark.
  - **Performance**: the switch is **one re-layout** (no re-render of the groups' contents), animation-free by default (respecting reduced motion), and the sizes are stored on drag end, not on each move.
  - **Tests**: the reducer/state (layout and sizes kept and restored), the segmented control (states, labels, keys, hidden with one group), the drop-zone function for both layouts as a **pure function** of the pointer and the box, the tab menu's words, and an end-to-end spec: open two groups, switch to stacked and **check the boxes** (the second group is below the first, the widths are equal), drag a tab to the bottom half, switch back, restart and see the layout kept, and a snapshot's frame **not reloading** across the switch.
  - **Decisions**: the default layout (side by side, as today); whether a narrow window **stacks by itself** (the recommendation: only as a suggestion in a notice, never silently); whether the two icons are the ones of the picture (drawn by us as SVG with the theme's tokens) or the codicons `split-horizontal` and `split-vertical`; and whether more than two groups (the next item) will use the same control as a **grid**.

## Development process: reviews of the code by plugins (priority Now, size S)
**Light use**: the user's weekly limit is finite, so nothing here runs unless the user asks for it in that message; the rule and the cheap way to work are in `CLAUDE.md`, "Light use".
Two plugins of the official Anthropic marketplace (`claude-plugins-official`) are installed for the user (`claude plugin install … --scope user`): **`claude-security`** (`/claude-security`: a scan of the whole repository or of **this branch's changes** by a team of agents that map the code, hunt for flaws and **try to disprove every finding** before it is reported; a report with severity and confidence, a SARIF file and, if asked, patches to apply by hand; it asks once to confirm its cost) and **`pr-review-toolkit`** (`/pr-review-toolkit:review-pr`: agents for code quality, **silent failures and error handling**, the **tests** a change needs, the **design of types**, comments, and **simplification**). Both run in the session, their agents in parallel, after `/reload-plugins` or in a new session. Reviewed before they were installed: neither has a daemon or network calls of its own; the hooks of `claude-security` only show a banner, count its own runs and suggest a scan after a push; **`security-guidance`** (hooks on every edit, a review of the diff by the model at every turn and on every commit, an SDK installed in a virtual environment) was **left out** on purpose because it spends tokens in the background all the time: it can be added if wanted.
- [ ] **When to run what**: `pr-review-toolkit` on **every pull request that changes application code**, before the merge; `claude-security` on **scan changes at high effort** for every pull request that touches **a parser, a writer, an IPC channel, a path of the file system, a process that is started, or the CSP**, and on the **whole repository** before each release; the findings are fixed in the same pull request or written here as items; the `CLAUDE-SECURITY-*` folders are never committed (they carry their own `.gitignore`); the cost is stated to the user before a scan is run
- [ ] The first **whole-repository scan** (effort `high`) of the code as it is today, and its report read and sorted into fixes and items here
- [ ] A line in `CLAUDE.md` (done) and in `CONTRIBUTING.md` for the people who contribute: what the reviews are and that the maintainer runs them
- [ ] Quality measures to add when a tool is chosen: coverage of the unit tests reported (not as a gate), a check of the size of the installer and of the start-up time on each release (the performance rule's "cost of arriving"), and `npm audit` of the dependencies before a release
