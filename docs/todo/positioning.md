## Positioning (decided in principle, after 0.1.3)
**"The safe workbench for the files that are not a project."** Browse, inspect, understand, fix and compare any file, inside archives too, **without sending anything anywhere and without trusting the file**. Folder Browser does not try to beat each specialist tool at its own job (a file manager, a hex editor, an image editor, a PDF tool, a folder-compare tool); it wins on **integration, safety and privacy**: one application, one interface (the one of VS Code, which people know), every format drawn in an isolated frame with no network, every write atomic and checked, signed releases and (planned) signed extensions, open source (MPL-2.0), on Linux, Windows and macOS.
- **Who it is for**: people who handle artefacts (support, QA, developers, system administrators), people who work with data files (CSV, SQLite, JSON), people who share files and care about what is hidden in them, and people who receive attachments of doubtful origin.
- **What it is honest about**: Electron costs memory and installer size; each feature is good enough rather than the best of its kind; the version is 0.1.x and nobody has used it on Windows or macOS yet; the team is small.
- **Competitors, from memory (verify each claim before it is published)**: Total Commander, Directory Opus, Double Commander, XYplorer (file managers; stronger at file operations, they do not preview or edit as many formats and do not edit inside a ZIP); File Viewer Plus, QuickLook, Seer, XnView MP (viewers); VS Code, Notepad++, Sublime, Zed (editors, made for projects); 7-Zip, PeaZip, Keka, Ark (archivers, no edit in place); ImHex, HxD, Okular, Stirling-PDF, Paint.NET, DB Browser for SQLite, Meld and Beyond Compare (specialists, the last one paid and the reference for comparing folders). **None joins** the isolated viewers, the safe in-place edit of ZIPs, comparing, hex, Office documents and the privacy promise in one open, cross-platform application.

## The three scenarios to polish and show (priority Next, size S each to demonstrate, the work they need is in the other area files)
- [ ] **Inspect a download safely**: open an unknown file or ZIP, see what it is (type, metadata, hidden data, the safety triage in `docs/todo/safety.md`) without running anything
- [ ] **Fix a file inside a ZIP**: open the ZIP as a folder, edit a text or a table, save it back in place with the Local History to undo
- [ ] **Compare two versions of anything**: two files, two folders, two pictures, two PDFs, two ZIPs (`docs/todo/compare.md`)
- [ ] For each: a **scripted end-to-end demo** (the way `npm run screenshots` drives the application) that records a short video or GIF and a checklist of what must work, kept as a test so the demo cannot rot

## Distribution channels (priority Next, size M)
Today the releases are `.deb`, `.rpm`, `.exe` and `.dmg` on GitHub. More people arrive through the channels they already use than through any feature.
- [ ] **Signed apt and dnf repositories** on GitHub Pages (a repository signed with a GPG key, the public key in the package and on the site), so that Linux users install with `apt` or `dnf` and **receive updates** (today a Linux package cannot be updated from inside the application); the packaging smoke test installs from the repository on a clean container
- [ ] **Flathub** (a Flatpak: the sandbox and its file-chooser portals fit the model of "roots the user chose", and the limits on Open With, trash and reveal are documented), **Homebrew cask** (macOS; smooth only when the app is signed and notarised), **winget** (a manifest pull request per release, with the installer's SHA-256), **Scoop** and **Chocolatey** (Windows), **AUR** (`folder-browser-bin`); each a small, automated step of the release (`scripts/release.mjs` opens the manifest updates, a human merges); AppImage and Snap stay **not planned** (strict confinement fights the file model)
- [ ] **Code signing**: Windows (a free programme for open-source projects such as the SignPath Foundation's, or Azure Trusted Signing: to check what applies) and macOS (the Apple Developer Program, US$99 a year, with notarisation) remove the SmartScreen and Gatekeeper warnings that drive people away; `docs/RELEASING.md`, "Signing", is the plan; the keys never live on CI
- [ ] **A site** (GitHub Pages, from `docs/site/`, built by a script): the positioning above, a **comparison table**, the features with screenshots, the three demos, **downloads detected by system** (links to the release assets with their checksums), the user guide rendered, the privacy statement, and later the **extension catalog** browsed from `index.json`; **no analytics** (download counts come from GitHub); English and Brazilian Portuguese
- [ ] **A first-run tour**: the first start offers **Open the Demo Folder** (the synthetic folder of `scripts/demo-folder.ts`, shipped with the application) and a short, skippable tour of the Explorer, the tabs and the command palette
- [ ] **Shell integration**: Windows installer entries (**Open with Folder Browser** on a folder, on the background of a folder and on any file; **Compare with Folder Browser** for two selected files), Linux `.desktop` actions and service menus for Nautilus and Dolphin, macOS Services; and a **command line** (`folder-browser <path>`, `folder-browser --diff a b`, `--wait`) that hands the request to a window that is already open (a second instance forwards and exits)
- [ ] **Portable mode** (priority Later, size S): a Windows build or a folder that runs from a USB stick and keeps its settings, drafts and history **beside itself**
- [ ] **Remote locations** (SFTP, SMB, WebDAV): **not in the core**; "nothing leaves the computer" is part of the positioning. What the system mounts as a folder already works; a connector, if ever wanted, is an **opt-in extension** (level 2, with a network permission) and a decision of its own
- Performance and safety: the tour and the site cost nothing at start; every channel serves the **same signed files**, and a release is published only after the checksums of the files on every channel match
- **Decisions to make**: the order of the channels (the recommendation: the apt/dnf repositories and winget first, then Flathub and Homebrew); whether to pay for the Apple programme; whether to apply for free Windows signing; the name and domain of the site; and whether a Flatpak build (with its smaller powers) is worth maintaining next to the native packages
