### Copy the path, and open a shell on a folder (after 0.1.3; priority Next, size S)
> **Reuse**: the **custom command template** (`{file}`, `{line}`, quotes, no shell) of `mdiff`'s `editor.ts` is the parser to port for the custom terminal command: see [`docs/ASSOCIATED-PROJECTS.md`](../ASSOCIATED-PROJECTS.md).
Two small commands in the right-click menu of the tree (and of a tab, and in Properties), for a row or for **several marked rows**. Today a tab's menu has **Copy Path** (the path inside its folder or snapshot) and the tree has **Reveal in File Manager**; the tree has no way to copy a path, and no way to start a shell in a folder.

Copy the path
- [ ] **Copy Path** (the full path of the disk, with the system's separators: `/home/me/work/a.txt`, `C:\Users\me\work\a.txt`), **Copy Relative Path** (from the folder that was opened: `docs/a.txt`), **Copy Name**, and **Copy as `file://` Address** (percent-encoded, for a browser or a document), each in the row's right-click menu and as keys (`Shift+Alt+C` for the path and `Ctrl+K Ctrl+Shift+C`-style relative path are VS Code's; the keys of Cut, Copy and Paste stay the file clipboard's), in the **tab's menu** and as a **Copy** button beside Location in Properties; a notice says what was copied ("Path copied")
- [ ] **Several rows**: one path **per line**, in the order of the tree; a **Copy as Quoted Path** variant (`'…'` on Linux and macOS with the quote inside the name escaped, `"…"` on Windows) so that a name with spaces or an apostrophe can be pasted into a shell as one word
- [ ] **Inside a ZIP or a snapshot**: the path of the file that holds it, then `!/` and the entry (`/home/me/pack.zip!/docs/a.txt`, nested as `a.zip!/b.zip!/c`: the same notation the application uses everywhere), and Copy Name and Copy Relative Path as above; the full path of a **real** file is given only when there is one (an entry has none: said in the menu's label, not left to fail)
- [ ] Written by the existing `copyText` call; nothing is read from the disk, and **nothing is resolved by the interface** (the full path is made by the main process from the root and the relative path, so the interface never builds a path of the disk), costing nothing

Open a shell on a folder
- [ ] **Open in Terminal** in the menu of a **folder** (and of the Files title, for the root, and **Open in Terminal Here** for a file: its folder), starting the system's **terminal with its shell already in that folder**; the shell is a **real program of the user's computer**, so it is opened only on a **real folder of an open root**, never on an entry of a ZIP or a snapshot (the item is greyed there, with the reason) and never on a path outside the roots (the path is resolved with the same checks as every operation: `resolveInside`, `realpath`, a link that leaves the root does not pass)
- [ ] **Which terminal**: a **list by system tried in order** and the first found is used: **Linux** `$TERMINAL`, `x-terminal-emulator`, then `gnome-terminal`, `konsole`, `xfce4-terminal`, `kitty`, `alacritty`, `wezterm`, `foot`, `xterm` (each with its own working-directory option); **Windows** Windows Terminal (`wt -d <folder>`), else PowerShell, else `cmd`; **macOS** the Terminal (`open -a Terminal <folder>`), or iTerm when it is installed and chosen; the choice and a **custom command** (a program and arguments with `{path}`, confirmed once, see "Settings") can be set in Settings ▸ System, and the **shell** is the user's own (their login shell, `$SHELL`, `COMSPEC`)
- [ ] **How it is started** (the security point): **no shell is used to start the terminal** (an argument list through `child_process.spawn`, `detached`, `stdio: 'ignore'`, `unref()`), the folder is passed as an **argument or as the process's `cwd`** and **never glued into a command string** (a name with a quote, a `$(…)`, a backtick, `&` or a leading `-` is data: a `--` before it where the program takes one), the environment is the application's own with nothing added from the file system, and a folder whose name is odd is tested; the application does not type anything into the shell
- [ ] If **no terminal is found** the item says so and points to Settings (the list of what was tried is shown); if the program **fails to start** a notice says which and why in plain words
- [ ] The old idea "Open a terminal here" under "Browsing" is **this item**; an integrated terminal inside the application (a pty and a view) is **not** planned (a native dependency, and the user's terminal does it better)
- [ ] Tests: the **choice of the program and its arguments as a pure function** (the platform, what exists, the folder, a custom command) for each system and each terminal, with names that have spaces, quotes, `$`, `&`, accents and a leading `-`; the copy variants for a file, a folder, several rows, an entry of a ZIP and a nested one, on both separator styles; the item greyed in a ZIP; a path outside the root refused; and an end-to-end spec in which a **made-up terminal program** (a script that writes its arguments and its working directory to a file, found through the setting or the `PATH`, as the Open With… specs do with `gio`) is started and the file is checked. Performance: the menu opens at once (the search for a terminal is made once, in the background, and kept), and starting it does not block the interface

### Permissions, owner, group and visibility (after 0.1.3; priority Next, size M)
An important part of handling files that the file managers hide or half-do (the GNOME Files, for one, does not let the user make a file executable from its properties in some versions, nor set the owner or the group): **see and change the permissions, the owner, the group and the visibility of a file or a folder**, for one row or for several, and for a folder's contents. Linux and macOS first (the Unix model), Windows after (attributes and ACLs, a different model). It writes, so the **safety rules apply**: only inside an open root, the path resolved with `resolveInside` and `realpath`, the item `lstat`ed (a symbolic link is the link, never the file it points to), arguments validated as `unknown`, no shell.
- [ ] **Properties ▸ Permissions** (and a quick **Make Executable / Remove Execute** in the right-click menu, `chmod +x` in one click, for a file and for several marked): a **grid of read, write and execute** for **owner, group and others**, the three special bits (**setuid, setgid, sticky**, each with a warning in words), an **octal field** (`755`) that edits the same value, the **symbolic form** (`rwxr-xr-x`) written beside it, and a **mixed state** (a dash) when several rows differ; a note for a folder that **execute means "enter"**
- [ ] **Owner and group**: the names shown (not only numbers; read from the system's user and group databases, with `getent` where the system uses NSS or a directory, started without a shell), the **group chosen from the groups the user belongs to** (what an unprivileged `chgrp` allows) and the **owner** shown; **changing the owner** (and a group the user is not in) needs privileges: offered as **Change as Administrator…** that runs a fixed `chown` through the system's authorisation (`pkexec` on Linux, the polkit prompt is the system's own; nothing is typed into a shell, the user and group come from the list, the path from the validated root), never silently, and said plainly when it is not possible
- [ ] **Apply to enclosed items** for a folder: **only files**, **only folders**, or **both**, with **add or remove** instead of set (for example "add execute to folders, leave files as they are": the usual `chmod -R u=rwX,go=rX`), a **count and a confirmation before it starts** ("this changes 12,430 items"), a **progress with Stop**, and a notice of what was changed and what could not be (a permission error is reported per item, never aborts the rest silently)
- [ ] **Guard rails**: removing the owner's own read, write or execute (or search on a folder) asks first ("you will lose access to this"); a **setuid or setgid** bit asks; a recursive change **on the root itself or on a system folder** asks harder; the **previous modes of what was changed are kept** (in the activity log, see "Safety and privacy tools") so that **Undo Permission Change** puts them back; the files of the trash and the `.wsnp` rules are untouched
- [ ] **Visibility** (the "hidden" of a file, which means something different on each system): on **Linux and macOS** a leading dot in the name, so **Hide** and **Show** are a **rename** (with the name check and the "never replace" rule) plus, for GNOME, the folder's `.hidden` list read and respected; on **macOS** the `hidden` flag (`chflags`) as well; on **Windows** the Hidden attribute (`attrib`/`SetFileAttributes`); a switch **Hidden** in Properties and in the menu, and the tree's "show hidden files" switch keeps its meaning; the "Hidden attribute of Windows" idea in "Ideas for later" is this item
- [ ] **More than the mode, read first**: the **time stamps** (modified, accessed, changed, and the birth time where the system gives it), the **SELinux context** (Fedora: the label as `ls -Z` shows it, with **Restore Default Context** as an opt-in `restorecon` through the local tool), the presence of **POSIX ACLs** and **extended attributes** (listed read-only first), the **immutable and append-only flags** (`lsattr`: a write that fails because of one says so in words), and on a **mounted disk** a note when it does not support Unix permissions (FAT, exFAT, NTFS, a network drive): the grid is greyed with the reason
- [ ] **Inside a ZIP**: the entries carry the Unix mode (the high bits of the external attributes, kept by `core/archive/edit.ts` today), so **Make Executable** and the grid work on **an entry of a ZIP** as an edit of the ZIP (written through the same safe rewrite); there is **no owner or group** in a ZIP, and the grid says so; later the same for a tar (which does keep owner and group)
- [ ] **Windows (later, size M)**: Properties shows the **attributes** (Read-only, Hidden, System, Archive) as switches, and a read-only **Security** list (the owner and the access control entries, from `icacls` or PowerShell, started without a shell and parsed); **editing ACLs** is the next item, "ACLs: access control lists"; **macOS** also shows its **ACLs** and **flags**, read-only first
- [ ] **In the tree and in new files**: an optional **Permissions** column (`rwxr-xr-x`, and the owner and group) in the size and date columns (see "Files" above), a marker on **executable files** and on files whose mode looks wrong (a world-writable file, a private key readable by others, a script with no execute bit, a folder with no `x`), the **umask** shown with the default modes **new files and folders** get, and a setting for a different default for the ones this application creates
- [ ] **The calls**: new validated `fb:` channels (`fb:fs-perms` to read the mode, owner, group, flags and context of one or more items; `fb:fs-chmod` with a mode or an add and remove set and a recursion mode; `fb:fs-chown`; `fb:fs-hide`), each taking a **root id and a path relative to it**, never a path of the disk, answering an `OpResult` with the **plain-words error** (`permission-denied`, `not-owner`, `read-only-filesystem`, `immutable`, `not-supported`); no `process.platform` reads in the interface (the interface gets the platform from `window.fb.platform`)
- [ ] **Performance** (the rule at the top): reading the permissions of a folder's rows is part of the listing's single `lstat` (no second call per row), the recursive change is a **streamed, bounded-concurrency walk off the interface's thread** with progress and cancel (100,000 items without a lost frame, and the first progress in under a second), nothing is read until Properties opens, and the Permissions column costs nothing when it is off
- [ ] **Tests**: `core/fs/ops.ts` tests in temporary folders for each mode change (add, remove, set; files only, folders only; a symbolic link left alone; a file that is not the user's; a read-only folder), a path that leaves the root refused, `chmod` on the root itself, the guard rails, the undo restoring the old modes, the group change to a group the user belongs to, the owner change through a **made-up `pkexec`** program (the real one is never started by a test), the visibility rename and its conflicts, the ZIP round trip of the mode (the entry keeps its other attributes), the octal and symbolic conversions as pure functions, and an end-to-end spec: open a folder, make a script executable from the menu, check the mode on the disk with `fs.stat`, change a folder's modes recursively and undo it
- **Decisions to make**: **Change as Administrator** (`pkexec`) in the first version or only **read** the owner and set the group among the user's own (the recommendation: include it, behind the system's prompt, since it is what the file managers lack); how far the **Windows** support goes (attributes only, or ACL editing); whether **visibility by renaming** is acceptable on Linux or a `.hidden` entry is preferred when the user does not want the name to change; and whether the **Permissions column** is on by default

### ACLs: access control lists (after 0.1.3; priority Later, size M to L; needs the permissions work above)
The mode of a file has three owners (the owner, one group, the others); an **ACL** gives **more**: access for **named users and groups** besides those, and **default entries on a folder** that new files inherit. Linux (POSIX ACLs), macOS and Windows each have one, and they are **different models**, so the plan is **one interface that shows each system's own truth** and never pretends they are the same. It is read first, then edited. It writes, so the safety rules of "Permissions" apply to every item: only inside an open root, the item `lstat`ed (a link is the link), arguments validated as `unknown`, **no shell**, a root id and a relative path, never a path of the disk.
- [ ] **Properties ▸ Access Control** (a tab beside Permissions, shown only where the file system and the system have ACLs; greyed with the reason where not: FAT and exFAT, some network drives, a system without the tools): the **entries** as a list (**owner**, **named users**, **owning group**, **named groups**, **mask**, **others**), each with **read, write and execute** switches, a **type and name** column showing names and not numbers, and for a **folder** a second list of the **default entries** (what new files and folders inside it receive); the plain mode of Permissions and the ACL's **mask** are shown as the same fact in two forms, with a note in words ("the mask limits what named users and the group can really do"), and the **effective permission** of each entry is shown beside what was set (a dimmed switch when the mask cuts it)
- [ ] **Edit**: **Add User…** and **Add Group…** (picked from the system's users and groups, read with `getent` started without a shell, plus the groups the current user is in; never a free-typed number unless the user turns that on), **change the switches**, **remove an entry**, **Remove All Extended Entries** (the `setfacl -b` that returns the file to the plain mode), **Copy ACL From…** another item of the open roots, and for a folder **Apply to Enclosed Items** with the same options as Permissions (files, folders or both, **add or remove**, a **count and a confirmation before it starts**, progress with Stop, per-item errors); all **through the system's `setfacl`/`getfacl`** (the `acl` package, present on most distributions: said in words when it is not) run **without a shell with an argument list**, a timeout and the validated path after `--`, because Node has no ACL call and writing the extended attribute by hand would mean a native module
- [ ] **Guard rails**: an edit that would **remove the user's own access** asks first; changing the **mask** or the **default entries of a root** asks harder; a **recursive** change on the root itself or on a system folder asks harder still; the **previous ACL of every item changed is kept** (a `getfacl` dump in the activity log, see "Safety and privacy tools") so that **Undo Access Change** puts it back; nothing is changed on the trash, on a `.wsnp` or on a path that leaves the root
- [ ] **A mark in the tree and the listing**: a small marker on the files and folders that **have extended entries** (the `+` that `ls -l` prints), a **filter** "with ACL", and a note when a **copy, move or ZIP** made by the application **does not keep the ACL** (a copy takes the destination's defaults; keeping them is an option for a later step, as is the same for extended attributes)
- [ ] **macOS**: the ACL entries of `ls -le` (the `allow`/`deny` entries with read, write, execute, delete, list, search, append and the inheritance flags) shown and edited through `chmod +a`/`-a` (started without a shell), read-only first; the Finder's **Sharing and Permissions** is the model for the simple view
- [ ] **Windows**: the **owner** and the **access control entries** (the user or group, **Allow or Deny**, the permission set: read, write, modify, full control and the advanced ones, and whether it is **inherited**) read with `icacls` or PowerShell `Get-Acl` (started without a shell, parsed), shown as the same list; **editing** a simple set (Users, Administrators, a named account: read, modify, full control), **inheritance** on and off (with the "convert to explicit entries" choice), **Take Ownership** and **Reset to Inherited** (through `icacls` and the elevation prompt of the system: `Start-Process -Verb RunAs`, never silently); the NTFS model is richer than the POSIX one, so the **advanced** entries are listed and edited only by an explicit "Advanced" view
- [ ] **Linux, the rest of the family**: **NFSv4 ACLs** (`nfs4_getfacl`, on NFS and some file systems) and **file capabilities** (`getcap`) are **read-only if at all**; the **SELinux context** stays in "Permissions" (a read and a `restorecon` opt-in); **Edit with the system's tool** (a button that opens the file's ACL in the user's own program) is a way out for what is not covered
- [ ] **Performance** (the rule at the top): the ACL of a file is read **only when Access Control is opened** (one `getfacl` call for a whole selection, not one per row), the marker in the tree comes from the **`+` of the listing's own stat information** or a cheap extended-attribute check in the same pass, a recursive change is a **streamed, bounded-concurrency walk off the interface's thread** (several items to one `setfacl` call where the tool allows), with a first progress in under a second and cancel
- [ ] **Tests**: the **parsing of `getfacl` and `setfacl` text** (and `ls -le`, `icacls`) as pure functions on hand-made output, including names with spaces and colons, numeric ids, the mask and default entries, and a malformed line; the validated arguments (a name that starts with `-`, a path with spaces, quotes and `$`: one argument each); a **made-up `setfacl` program** that records its arguments, so a test never changes a real ACL; the guard rails, the undo restoring the dump, a path leaving the root refused, a file system with no ACL support, and an end-to-end spec that, **where the machine supports ACLs**, adds a named group on a temporary folder, checks it with the system's `getfacl`, and undoes it (skipped, with a note, where `setfacl` is absent)
- **Not planned**: editing **file capabilities** (`setcap`), **SELinux policy** (`semanage`), **AppArmor profiles**, and **auditing rules**
- **Decisions to make**: whether the first version is **read-only** (the recommendation for the first release: show the entries and the effective permissions, mark the `+`) with editing in the next; whether to **depend on the system's `setfacl`** (the recommendation) or ship a small native helper; how far **Windows** goes (a simple editor, or the full ACL with inheritance); whether the **copy and move keep ACLs** by default; and whether **Edit as Administrator** (polkit on Linux, the elevation prompt on Windows) belongs here or only in "Permissions"

### Sizes and counts of folders (after 0.1.3)
Today **Properties** shows a file's size in bytes, and a folder shows none: the tree knows only the files of a folder it has listed, not what is below. A total is a walk of the whole folder, so it is made **on demand, in the background, and never by the interface's thread**; what the tree already knows costs nothing and is shown at once.
- [ ] **Properties of a folder (and of the Files root)**: the number of **files** and of **folders** (also how many are hidden), the **total size in bytes** (exact, with thousands separators, and in KB/MB/GB beside it), and the number of items that **could not be read**; the numbers **count up while it works** (a few times a second) with **Stop**, and the walk ends when the dialog closes; a reading is done by the main process (`fb:fs-measure`, arguments validated as `unknown`, a root and a path inside it, a token to cancel), read-only, never following a symbolic link (the link is one item of its own size), counting a **hard link once**, not crossing onto another file system (as `du -x`: a mounted network drive is not walked by accident), and looking at the folders with a bounded number of reads at a time
- [ ] **Several rows marked**: Properties of the selection gives the sum (files, folders, bytes) of everything marked; and the **status bar** says what is marked or in front ("3 selected, 12.4 MB" for files; for a folder "N items", from the listing, with the total offered on a click)
- [ ] **The size of an archive and of what is in it**: a ZIP (and a `.wsnp`) has its entries, their **unpacked** and **packed** sizes and the ratio, read from its central directory at once (no walk); a folder inside a ZIP the same; **Size on disk** (the blocks the folder takes: Linux and macOS) as a second line where the system says it
- [ ] **In the tree, with no extra cost**: a tooltip on a folder that is open or was listed says "12 files, 3 folders, 4.2 MB in the files directly inside"; a **Calculate Size** item in a folder's right-click menu shows its total (the walk above) in the row, kept until the folder changes (a refresh or a file operation of the application drops it) and never run for every folder by itself
- [ ] **A size column** (the open item "Columns for size and date" above): files show their size; a folder shows its total **once it was calculated**, with an optional **Calculate Folder Sizes** setting that works through the folders in view in the background (a few at a time, cancelled when the folder is closed, never in a folder with more than a limit of entries without asking)
- [ ] Tests: the walk over a hand-made tree (counts of files, folders and hidden, bytes, a symbolic link not followed and not counted twice, a hard link counted once, an unreadable folder counted as an error, a cancel in the middle, a loop made by a link); the dialog counting up and stopping; a ZIP read from its directory; the tooltip text from a listing; and an end-to-end spec on a folder of known files whose bytes equal the sum of the fixtures. A budget: a folder of 100,000 small files is counted without a frame of the interface being lost, and the first numbers come in under a second

## Safety net: local history and a tree that follows the disk (after 0.1.3; priority Now, size M each)
Two things that make every other feature safer. **Local History**: the application writes over originals (text, a ZIP, and soon PDFs and pictures), and a save that goes wrong or is regretted has no way back except the trash. **Live refresh**: the tree does not notice a file that is created, renamed, changed or deleted by another program (there is no watcher today), and several plans (search folders, "changed on disk", logs) need to.

Local History
- [ ] Before every write the application makes over an existing file (Save of a text, bytes, a table, a PDF, a picture, a playlist; a ZIP rewritten; Replace in Files; a move that replaces nothing needs none), the **previous version is kept** in the application's own folder (`userData/history/`, a folder per file named by a hash of its root and path), as a **compressed copy** (gzip; a changed ZIP or a big file keeps a **reference by hash** instead of a second copy where the same bytes are kept once: a content-addressed store), with the time, the size and what made it ("Save", "Replace in Files")
- [ ] **Versions…** in the right-click menu of a file and on the toolbar of an editor: the list of versions (date, size, what), **Compare with Current** (the diff that exists), **Open** (read-only tab), **Restore** (itself kept as a version first) and **Save a Copy**; a deleted file's versions stay and are found from its folder's menu (**Restore deleted…**)
- [ ] **Limits that keep the disk safe**: a total size (500 MB by default), a number of versions per file (50), an age (30 days), whichever comes first, the oldest dropped first; a file bigger than a limit (100 MB) keeps no version unless chosen; a setting to turn it off and a button to clear it; never in the places the user did not open (a version belongs to a root) and never for what is read-only
- [ ] The versions are **written off the interface's thread**, after the original is safely renamed (a failure to keep a version never fails the save: a notice says so), with **streaming** for a big file and a hard link or a reflink where the system gives it (no copy); the store is **content-addressed and pruned by one pass at start**, never a scan of the whole history on each save
- [ ] Tests: a save keeps the old bytes; Restore brings them back and keeps the current; the limits drop the oldest; a deleted file is found; a corrupt entry is skipped in plain words; a budget (a save of a 10 MB file adds under 50 ms to the user's wait, and the history of 10,000 versions lists in under 200 ms); an end-to-end spec (edit, save twice, compare, restore)

Live refresh
- [ ] A **watcher on the folders the tree has open** (not on the whole root: the folders expanded and the root's top, with `fs.watch` where it is reliable and a short poll as a fallback for the network drives; the limit of `inotify` watches on Linux is read and respected), events **debounced** (a few hundred ms) and merged, so a `git checkout` or an unzip of 10,000 files is one refresh, not 10,000
- [ ] The tree **keeps its place** (expanded folders, the marked rows, the scroll, the focus) while rows appear and go; a new file is **not** stolen into focus; a folder deleted outside closes its tabs' file with the same notice as a delete from inside, and a file **changed on disk while its tab is open** reloads when the tab is clean and warns when it has changes (the open item under "Text editing")
- [ ] **Files being written** (a download, a copy in progress) are shown when they settle, not at each growth; a setting to turn the watcher off and a manual **Refresh** that always works
- [ ] Performance and tests: the idle cost is nothing (no polling of a folder that is not shown, watchers released when a folder collapses or a root closes), a burst of 100,000 events keeps the interface above 30 frames, memory is bounded; tests with a fake watcher for the merging and the debounce, a real-disk end-to-end spec (create, rename, delete, change from outside the application), and the limit of watches reached (said, with a manual refresh offered)

## Tools for files: checksums, duplicates, bulk rename and disk usage (after 0.1.3; priority Now for checksums, Later for the rest)
- [ ] **Checksums** (priority Now, size S) in Properties of a file and in the right-click menu (**Checksums…**): MD5, SHA-1, SHA-256 and SHA-512, computed **as a stream in the background** (progress and Stop for a big file, never the whole file in memory), with a **Compare** box to paste a hash (or a `sha256sum` line) that says Match or Different, **Verify with a file** (a `.sha256`, `.md5` or `SHA256SUMS` beside it: every file named in it is checked, a table of OK, FAILED and missing), and **Copy**; for an entry of a ZIP the CRC-32 it declares is shown at once; a budget: 1 GB hashed without a lost frame and at disk speed
- [ ] **Find duplicate files** (priority Later, size M): in a folder's menu, by **size, then the first and last blocks, then the full hash** (so most files are never fully read), grouped, with the **oldest or the one in the shortest path suggested to keep**, a preview, and **Move the others to the trash** after a confirmation that names how many and how big (never automatic, never across roots); the result can be kept as a **search folder** (see "Search folders"); streamed, cancellable, with a budget on a folder of 100,000 files
- [ ] **Bulk rename** (priority Later, size M): on the marked rows, a dialog with a **pattern** (`{name}`, `{n}` with a start, step and zeros, `{date}` from the file or from the **EXIF or tags** with the shared metadata reader), **find and replace** (also regular expression), **case**, **extension**, a **live preview** of every old and new name, conflicts (two with the same new name, one that exists) shown and blocking, applied through the safe rename (never replacing), as **one undoable step** and one notice
- [ ] **Disk usage map** (priority Later, size M): a **treemap** (and a sorted list) of what takes the room under a folder, drawn on a canvas from the walk of "Sizes and counts", with a click to go into a folder and a right-click to open it in the tree; the walk is the same one, cancellable, and the picture keeps 60 frames with 100,000 rectangles by merging the small ones
- [ ] Tests for each: hand-made trees, a `SHA256SUMS` with a bad line, the order of the checks of duplicates (it never reads a full file whose size or edge differs), the preview of a rename with conflicts and its undo, and the treemap's layout as a pure function
